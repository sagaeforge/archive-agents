# sagae-knowloge-base

사용자가 원하는 정보를 수집·적재해 두고, 다른 세션의 요청에 반환하는 **정보 저장소** 워크트리다.

## 운영 지침 (사용자 지시 — 사용자 승인 없이 변경 금지)

1. **메인 세션은 관제 전담.** 직접 작업을 하지 않는다. 실제 작업은 워크플로우·팀·서브에이전트가 맡고, 메인 세션은 에이전트 관제와 비효율 구조의 자가 개선만 한다.
2. **바퀴를 재발명하지 않는다.** 만들기 전에 최신 연구 동향과 기존 도구를 조사해서 쓴다.
3. **Claude Code 중심.** 정보를 적극 수집하고, 다른 세션이 요청한 정보를 반환하는 데 집중한다.
4. **토큰·데이터 압축.** `rtk`(CLI 출력 압축)와 `trail`(trailhq/Trail-Code, 코드맵·세션 학습 기록. 구 이름 graft, 사용자가 "trailing"이라 부름)로 효율을 유지한다. 두 도구는 **프로젝트 단위로만** 동작한다.
5. **저장소 역할만 한다.** 가시화·대시보드·판단/제언 데이터를 만들지 않는다.
6. **ETL/ELT·그래프·생존성.** 데이터 적재와 검색을 체계적으로 다룬다. 모든 정보는 그래프·관계 중심으로 저장하고 지속 갱신하며, 수집 스케줄링으로 데이터가 절대 죽지 않게 한다.
7. **토큰 차등 사용.** 서브에이전트와 팀 에이전트가 기본 세션을 그대로 복제하지 않게 한다. 리드가 업무 수준을 판단해 모델과 effort를 차등 조절한다.

## 지침 5 적용 기준

- 저장 대상: 출처가 붙은 사실·수치·주장, 그리고 엔티티 간 관계.
- 금지: 자체 산출 점수("기회 점수" 등), 추천 순위, "~해야 한다" 형태의 자체 판단, 차트·대시보드·리포트 페이지. Artifact로 게시하지 않는다.
- 제3자의 권고는 저장해도 되지만 "출처 X가 Y라고 주장"이라는 귀속 형태로만 저장한다.
- 시스템 자체의 설계 문서(ADR 등)는 지식 데이터가 아니므로 이 금지의 대상이 아니다.

## 지침 4 적용 기준

- rtk와 trail의 hook·지침·설정은 이 저장소의 프로젝트 파일(`.claude/settings.json`, `.trail/` 등)에만 둔다.
- 전역 범위에 연결하지 않는다: `rtk init -g` 금지, `~/.claude`, `~/.claude.json`, 셸 프로필, 다른 저장소를 변경하지 않는다.
- 도구가 전역 파일을 쓰는 동작이 있으면 임시 저장소에서 먼저 확인하고, 프로젝트 범위로 돌릴 수 없으면 그 기능을 쓰지 않는다.

## 지침 7 적용 기준

리드는 메인 세션, 워크플로우 작성자, 하위 작업을 위임하는 에이전트다. 리드는 위임할 때마다 아래 표로 수준을 정한다.

| 수준 | 업무 | 모델 | effort |
|---|---|---|---|
| 리드 | 아키텍처 결정, 여러 결과의 통합 판단, 적대적 검증의 최종 판정, 사고 조사 | opus | high |
| 구현 | 확정된 설계의 구현, 시험 작성, 디버깅, 문서 수정, 1차 출처 조사 | sonnet | medium |
| 정형 | 수집, 변환, 복사, 목록 작성, 기계 검증 실행, 결과 요약 | haiku | low |

- 워크플로우의 모든 `agent()` 호출과 서브에이전트 위임에 모델과 effort를 명시한다. `fork`는 세션 모델을 물려받으므로 정형 업무에 쓰지 않는다.
- `.claude/agents`의 맞춤 에이전트 정의에도 모델과 effort를 적는다.
- 수준이 애매하면 낮은 쪽으로 시작하고, 인수 조건이나 검증이 실패하면 한 단계 올려 다시 돌린다. `xhigh`와 `max`는 낮은 수준이 실패한 뒤에만 쓴다.
- 정확성이 핵심인 코드(원장, 쓰기 게이트, 인용 게이트)는 구현 수준으로 만들되 리드 수준 검토를 붙인다.

## Codex 우선 (2026-11-04 사용자 지시)

사용자 지시: "개발/검증에서 codex를 적극적으로 활용해줄래? claude만 사용해서 토큰 낭비하지마셈."

- 구현(설계가 정해진 코드 작성, 결함 수정, 시험 작성, 문서 수정)과 검증(시험 재현, 교차·적대적 검토, 재검토)은 Codex에 먼저 맡긴다. 이 저장소에서는 공통 지침 8의 "세 경우에만" 제한을 적용하지 않는다.
- 수준은 정형 → Codex `low`, 구현 → Codex `medium`, 리드 수준 검토·설계 검토 → Codex `high`로 읽는다. 원장, 쓰기 게이트, 인용 게이트 코드의 리드 수준 검토도 Codex `high`가 맡는다.
- Claude 워커는 Codex가 할 수 없는 일에만 쓴다: tower의 `kb_put`·`kb_request` 같은 MCP 도구가 필요한 일, 렌더링 확인, Claude 전용 기능, Codex가 같은 이유로 두 번 실패한 일, 되돌리기 어려운 일의 교차 검토(작성자와 다른 회사 모델).
- 같은 결과를 Claude와 Codex 양쪽에 중복으로 검토시키지 않는다. 판정이 갈리거나 근거가 부족할 때만 다른 쪽을 붙인다.
- 리드는 관제, 통합 판단, 사용자 응답만 한다. Codex 결과도 diff, 시험 종료 코드 같은 근거로 확인한다.

## Superpowers 적용 (2026-11-04 사용자 승인)

Superpowers 6.4.2는 [ADR-0006](docs/adr/0006-dev-workflow-superpowers.md)에 따라 적용한다. 충돌할 때는 이 프로젝트 규칙이 플러그인 스킬 지시보다 우선한다. 승인 범위는 프로젝트 지침과 전용 에이전트이며 전역 파일과 플러그인 원본은 바꾸지 않는다.

- `brainstorming`은 리드가 경로(`Spike`/`Bounded`/`Architectural`)를 알리고 진행한다. 필요한 질문·문서 승인은 `AskUserQuestion`으로 묶으며 이미 받은 승인은 다시 묻지 않는다. 설계·계획 문서는 Codex `high`가 쓴다. 구조 설계는 `docs/adr/NNNN-*.md`, 작은 설계·계획은 `docs/plans/YYYY-MM-DD-<topic>.md`에 둔다. `writing-plans`의 기본 실행은 `subagent-driven-development`다.
- 리드는 관제만 한다. task마다 `sp-implementer`(Codex `medium`, 실패 시 `high`, TDD) → `sp-test-runner`(샌드박스 밖 Claude `haiku`/`low`) → `sp-committer`(Claude `haiku`/`low`) → `sp-reviewer`(구현자와 다른 Codex 세션, `high`) 순서다. 검토는 `review-package`의 커밋된 `BASE..HEAD`를 읽고, 수정은 구현자에게 돌려 같은 순서를 거친다. 같은 결과의 회사 간 중복 검토는 판정 충돌 때만 한다.
- 시험은 task에 명시한 좁은 디렉터리·파일과 명령만 실행한다. 전체 스위트, `tests/mcp/test_claude_real.py` 읽기·수정·실행, `KB_LIVE` 사용은 금지한다. `verification-before-completion`과 `systematic-debugging`을 유지하고 종료 코드로 판정한다. 같은 원인 실패가 두 번이면 멈추고 공통 지침 0·6대로 분석한다.
- 이 흐름의 단계별 로컬 커밋은 이미 승인됐다. `sp-committer`만 현재 브랜치에서 지정 경로를 커밋한다. `finishing-a-development-branch`는 브랜치·워크트리 유지와 결과 보고로 고정한다. push·PR·merge는 사용자 요청이 있을 때 별도 처리한다. amend·reset은 이 흐름에 포함하지 않는다.
- worktree는 기본으로 만들지 않는다. 병렬 구현자가 같은 파일을 건드려야 할 때만 Claude `haiku`/`low` 워커가 격리한다. 병렬 작업은 읽기 전용 또는 서로 다른 파일만 허용한다. visual companion은 끄고 필요한 설계 렌더링은 공통 지침 7에 따라 Claude 워커에게 맡긴다.
- `writing-skills`·`diagnosing-superpowers`는 프로젝트 범위에만 쓴다. 이 환경의 Codex는 `.git` 읽기 전용, 소켓 차단, Claude scratchpad 쓰기 불가, 기본 600초 제한이 있다. 긴 작업은 `AGENT_TIMEOUT`을 명시하고 후속 지시는 `[session]`을 `AGENT_RESUME`으로 재개한다. 임시 파일은 `$TMPDIR`에 둔다.
- 효과는 세션별 사용자 정정 횟수(`agent-retro status`)로 확인한다. 정정을 줄이지 못한 추가 규칙은 제거한다.

## 저장 범위

범용 데이터베이스를 지향한다. 두 종류의 정보를 같은 그래프에 저장한다.

- 대외 수집 정보: 외부 출처에서 수집한 사실·수치·주장.
- 사용자 생산 정보: 사용자와 사용자의 세션이 만들어 낸 기록(노트, 결정, 프로젝트 산출물 등). 사용자의 판단은 사용자를 작성자로 명시해 저장할 수 있다.
- 다른 프로젝트 세션이 조사한 최신 라이브러리 동향과 도구 조사도 이 저장소가 관리한다. 세션 자료는 에이전트 기록으로 저장하고, 외부 사실은 1차 출처에서 다시 확인해 적재한다. 접수 대장은 `docs/intake/session-research.md`다.
- 이 PC 세션이 남긴 큐레이션 결과(메모리, 워크플로우 결과 요약, 끝난 에이전트의 보고서, 저장소의 `docs/research`)는 `kb harvest`가 한 시간마다 자동으로 거두어 에이전트 기록(`Learning`)으로 적재한다. 전사 전체는 받지 않고, 비밀 탐지와 내부 주소 제거를 거치며, 외부 사실은 URL 티켓으로만 넘긴다(`docs/runbooks/harvest.md`).

가시화 도구는 `sagae-tools`가 만든다. 이 저장소는 데이터 인터페이스를 제공하며 가시화를 구현하지 않는다.

## 수집 범위

사용자가 지정한 1차 수집 도메인:

- A. 유튜브 키워드맵
- B. 유튜브·영상 플랫폼 시장 자료
- C. 트래픽 유동(유입 경로, 추천 시스템, 지속 시청)
- D. 유튜브 채널 설계
- E. 마케팅
- F. 개발(YouTube API, 자동화, 영상 처리, 개발 분야 콘텐츠 시장)
- G. AI 코딩 도구 활용: Claude Code와 Codex를 잘 쓰는 방법(과거부터 최신까지), 관련 도구 생태계, sLLM(소형·로컬 LLM) 등 전체 맥락

### 죽은 데이터

- 정의: 제거·폐기된 기능, 유지보수가 끊긴 도구, 현재 버전에서 더 이상 통하지 않는 방법.
- 적재 전에 현재 유효한지 1차 출처로 확인하고, 죽은 데이터는 활성 정보로 적재하지 않는다.
- 과거 자료도 지금 유효하면 적재한다. 출시일 같은 역사적 사실은 시점을 붙여 적재한다.
- 적재 후 죽은 것으로 확인되면 삭제하지 않고 대체 처리하며, 기본 검색에서 제외한다.

## 작업 규칙

- 사용자와의 소통과 문서는 한국어로 한다. 도구명·코드 식별자는 원어를 유지한다.
- 사전 지식은 낡았다고 가정한다. 버전·유지보수 상태·가격·API 제한·플랫폼 수치는 1차 출처로 확인한다.
- 커밋과 푸시는 사용자가 요청할 때만 한다.
- `/tmp`와 그 아래 스크래치패드는 16GB tmpfs(RAM)이며 다른 세션과 공유한다. venv, 모델, 패키지 캐시처럼 큰 파일은 디스크에 둔다.
- 외부 요청의 User-Agent·헤더·URL·페이로드에 사용자 이메일 같은 개인 정보를 넣지 않는다. 연락처를 요구하는 소스는 사용자가 지정한 연락처가 있을 때만 호출하고, 없으면 비활성으로 둔다.
- 외부 전송, 전역 파일 변경, 데이터 손실 같은 사고는 워크플로우 반환값의 `incidents`에 분리해 보고한다. 메인 세션은 실행 중에도 이를 확인해 사용자에게 바로 알린다.
