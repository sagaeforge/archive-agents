# ADR-0005 FW1~FW9 구현 계획

> **에이전트 실행 지침:** 필수 스킬은 `superpowers:subagent-driven-development`다. 승인된 실행 방식을 유지하고 아래 checkbox를 task별로 추적한다. 이 문서는 구현 전 내용 검토용이며, 사용자 검토가 끝나기 전에는 구현을 시작하지 않는다.

상태: 검토 대기
갱신일: 2026-11-05

**Goal:** loupe가 KB의 first_party 문서·메모·주제·검토 결정을 안전하게 저장하고 연구를 요청하도록 ADR-0005의 FW1~FW9를 구현하며, 사용자는 계약 fixture·좁은 시험 근거·FW7 검토 기록·FW8 입회 결과로 확인한다.

**Architecture:** 기존 `kb serve`의 HTTP `/v1`과 `KB_HOME/run/read.sock`에 인증된 쓰기를 연결하고 `put_record`, `tombstone_record`, `engine.commit`의 공통 원장 경로를 사용한다. 잠금 안의 대상·멱등·판·한도 검사, 현재 원본에 따른 읽기 가시성, 연구 예산 예약을 공유한다. 사람의 공개·해제 동작은 별도 `reviewer` 범위와 WebAuthn 증명을 요구하며, FW7과 FW8을 통과해야 운영 쓰기를 켠다.

**Tech Stack:** 기존 Python `>=3.14`, SQLite 원장·투영, CAS·스풀, Starlette·Uvicorn, JSON Schema·OpenAPI, pytest, `ops/bin/dev`, `ops/bin/contract-check`를 재사용한다(`pyproject.toml`, `ops/bin/dev`, `ops/bin/contract-check`). WebAuthn 라이브러리는 ADR 6.8의 후보 `py_webauthn`을 포함해 FW9에서 1차 출처와 설치 환경을 확인한 뒤 선택한다. 이 계획은 버전이나 설치 완료를 가정하지 않는다.

**Spec:** [ADR-0005 승인 9판](../adr/0005-first-party-write-api.md), 특히 [9장 작업 패키지](../adr/0005-first-party-write-api.md#9-작업-패키지). 실행 계약은 [ADR-0006](../adr/0006-dev-workflow-superpowers.md)과 [계획 문서 규칙](README.md)을 따른다. 아래의 `ADR n.n`은 ADR-0005의 절을 뜻한다.

## Global Constraints

- 이 계획 승인과 구현 완료는 별개다. 지금 만드는 산출물은 이 문서 하나이며 코드·시험·설정·운영 데이터·토큰을 변경하지 않는다.
- 구현은 현재 브랜치에서 task별로 직렬 실행한다. 같은 파일은 한 구현자만 소유하며 공유 파일의 소유권은 이전 task 검토 후 넘긴다. 기본 실행을 다시 선택하지 않는다.
- 일반 HTTP 쓰기의 `actor=app:<라벨>`이며 `change=save|autosave|auto`, 주장된 작성자는 허가 근거가 아니다. WebAuthn으로 검증한 FW9의 사람 동작만 `actor=user:sagae` 예외다(ADR 3.2, 6.8).
- `editor`는 `Page`, `Note`, `TopicSpec`, `Review`만 쓴다. 새 기록 기본 `private`, `secret`·격리·redact 대상은 숨기며 없는 대상과 같은 404다. 민감도 하향은 사람 증명을 요구한다(ADR 3.4, 3.6).
- 모든 쓰기는 Unix 소켓에서도 Bearer 필수다. 무토큰·`viewer` 읽기는 `internal` 이하, 인증된 `editor`·`reviewer` 읽기는 `private` 이하이며 잘못된 Bearer는 401이다(ADR 3.1, 3.3, 8장).
- 요청 2 MiB, UTF-8 본문 1 MiB, 제목 300자, 정규 JSON `props` 16 KB, 링크 500개다. 단위와 경계는 ADR 4.5 그대로 사용한다.
- 토큰별 분당 120·순간 20, 쓰기 동시 2, 읽기 동시 16, `autosave`·`auto` 새 판은 30초에 1판, 연구 요청 하루 5회다. 요청 제한을 쓰기 허가나 예산 대신 쓰지 않는다(ADR 2.2, 3.5).
- 원장 증가는 최근 24시간 actor별 32 MB·기록별 8 MB다. 스풀 보유는 토큰별 64 MiB·200건, 전체 256 MiB·400건이며 `failed`는 하루 한도가 아니라 보유 상한에 센다(ADR 5.8).
- 비밀 검사는 CAS·스풀·보류·원장·재생 조회보다 앞이다. 식별자 비밀과 클라이언트 키의 NUL은 모든 통로에서 거절한다. HTTP 내용은 기본 거절, 기존 MCP·inbox·CLI 내용 격리와 위키 링크 규칙은 유지한다(ADR 2.3, 5.1, 7장, 9장).
- 연구는 TP1·TP5·D5 완료 뒤 연결한다. 세 단위 예산은 주제 월 기본 $10·HTTP 주제 전체 월 $30·엔진별 상한이며, `sending` 뒤 불확실 예약은 반환하지 않는다(ADR 6.4). K-c 미결 동안 해당 유료 에이전트 경로는 409 `budget_unavailable`이다(ADR 6.9).
- `private` 연구의 외부 질의·외부 LLM 호출은 0이다. publish 외부 정제는 메모 판·실제 전송 해시에 묶인 `publish_external_refine` 동의 후에만 허용하며 결과 공개는 별도 `publish` 확인을 요구한다(ADR 5.10, 6.6, 14.8).
- `private_open`은 FW2·FW4·FW5와 모든 읽기 가시성이 준비됐을 때만 참이다. `editor_routes`와 `hitl.available`도 실제 준비 상태만 광고한다. 규칙 artifact가 없거나 판·해시가 다르면 편집기 준비 완료를 광고하지 않는다(ADR 7.7, 8.1).
- 제품 시험은 아래 task가 지정한 파일·디렉터리만 `ops/bin/dev`로 실행한다. 전체 스위트, `tests/mcp/test_claude_real.py` 읽기·수정·실행, `KB_LIVE`, 실제 LLM 호출은 금지다. 외부 어댑터·WebAuthn·시간·장애는 합성 입력과 대역으로 시험한다.
- 임시 파일은 디스크 `$TMPDIR` 아래에 둔다. 시험 실행자는 `KB_LIVE`를 해제하고 운영 경로가 아닌 `KB_HOME`·설정 경로를 명시한다. 운영 환경 스크립트나 권한 우회로 시험을 통과시키지 않는다.
- FW7 최종 통과 전 운영 쓰기를 켜지 않는다. FW8의 소켓 재시작은 좁은 끝단 시험·검토 이후 질문 도구로 받은 명시적 사용자 승인과 입회가 있어야 한다. 이 계획 승인으로 재시작 승인을 갈음하지 않는다.

## Review Focus

1. **응답 유실·다른 앱의 같은 키·뒤늦은 숨김:** 재생이 중복 기록을 만들거나 현재 숨은 내용을 돌려주지 않아야 한다. FW3의 `test_idem_namespace.py`, `test_replay_visibility.py`와 FW6의 `test_research_replay.py`가 담당한다.
2. **비밀 속성 이름·한글/보조 평면 문자·dry-run:** 값이나 경로 힌트가 진단·로그·저장소에 남지 않고 코드포인트/UTF-16 구간이 맞아야 한다. FW1의 합성 벡터와 FW3의 `test_secret_editor.py`가 담당한다.
3. **게이트 경합·스풀 중 종료·오래된 실패 사본:** 202 전에 예약이 내구 저장되고 실패 본문은 하루 쓰기를 막지 않으며 보유 상한을 넘지 않아야 한다. FW4의 `test_spool_quota.py`, `test_failed_write_body.py`가 담당한다.
4. **원본 민감도 상향과 낡은 투영·옛 판:** 재투영 전·재시작·재구축 후에도 파생 문장·근거·관계가 일반 읽기에 새지 않아야 한다. FW5의 `test_derived_sensitivity.py`, FW6의 `test_research_sensitivity.py`가 담당한다.
5. **사람 확인 전 외부 호출·전송 재시도·확인 간 혼용:** reviewer 토큰만으로 전송하거나 공개하지 못하고, 바뀐 payload·결과·엔진에는 새 증명이 필요하다. FW9의 `test_publish.py`, `test_publish_async.py`, `test_reviewer_trust.py`와 FW7 검토가 담당한다.

## 실행 순서와 인계

task 번호는 FW 번호에 맞추며 실행 순서는 **FW1 → FW2 → FW3 → FW4 → FW5 → FW9 → FW6 → FW7 게이트 → FW8 게이트**다. FW6은 ADR-0004 TP1·TP5·D5 완료 근거를 받은 뒤 시작한다. FW9의 외부 정제도 E1/D5 미배포 시 로컬 대체로 닫는다. FW6 지연 중 FW7 예비 검토를 하더라도 최종 통과로 계산하지 않으며 FW6과 FW9를 포함한 최종 범위를 다시 검토한다(ADR 9장 순서).

task마다 `sp-implementer` **Codex `gpt-6.1-sol`, medium, 실패·낮은 확신 시 high** → `sp-test-runner` **Claude Haiku low, Codex 샌드박스 밖** → `sp-committer` **Claude Haiku low**의 지정 경로 로컬 커밋 → `sp-reviewer` **별도 Codex `gpt-6.1-sol` 세션, high, 읽기 전용** 순서를 따른다. 구현 세션과 검토 세션은 반드시 다르고 `AGENT_TIMEOUT=1800`을 명시한다. FW7은 독립 교차 검토가 주 작업이며 FW8의 운영 행위는 사용자가 맡는다.

실행 때만 `.superpowers/sdd/2026-11-05-adr-0005-fw-plan/` 아래 task별 brief·report·manifest·로그·review package를 만든다. 리드는 task 시작의 `BASE`, 전체 작업 시작 SHA, expected HEAD·브랜치·파일 소유권·허용 시험 경로를 고정한다. 출력 봉투는 완료 기준별 통과 여부, 명령별 실제 종료 코드, 재시도 횟수, 세션 ID, 미실행·미해결·사고와 근거 경로다. `sp-test-runner`의 검증 전후 SHA-256과 커밋 내용을 대조하고, `sp-committer`가 설치된 `review-package`에 plan·BASE·HEAD·명시적 출력 **파일** 경로를 전달한다(ADR-0006 task별 순서).

행동 변경은 task의 새 시험 작성 → RED 확인 → 최소 구현 → GREEN 순서다. Codex에서 소켓 때문에 RED가 막히면 `BLOCKED`로 인계하고 `sp-test-runner`가 실행한 뒤 같은 구현 세션을 재개한다. 문서·스키마만 바꾸는 단계는 정적 검증을 사용한다. Critical/Important는 수정 → 좁은 검증 → 새 로컬 커밋 → 수정 범위 독립 검토를 마쳐야 닫힌다. 같은 원인 실패 두 번이면 중단·원인 분석한다.

아래 검증 명령은 저장소 루트 기준이며 **이 계획 작성에서는 실행하지 않는다**. 실행 역할이 매 검증 환경에 다음을 먼저 적용하고 task별 명령의 종료 코드를 각각 기록한다. 기존 툴체인 접근 불가나 `contract-check` 의존성 준비 실패는 `BLOCKED`로 보고한다.

### Task 1: FW1 — 계약 0.4.0과 공개 비밀 규칙

**목적과 사용자 확인 결과:** loupe가 추정 없이 요청·응답·오류·준비 상태를 구현하도록 계약 0.4.0, 11종 fixture와 비밀 규칙 artifact를 제공한다. 사용자는 계약 검사 출력과 파일에서 확인한다.

**목표:** ADR 2.2~2.4, 5.6, 7장, 8.1, FW1의 인터페이스를 고정한다.

**Files / 수정 범위:**

- Modify: `docs/contracts/openapi.yaml`, `docs/contracts/data-interface-v0.md`, `docs/contracts/CHANGELOG.md`, `docs/contracts/fixtures/requests.yaml` 및 기존 fixture 생성·검증 파일 `tests/contract/gen_fixtures.py`, `tests/contract/test_fixture_cases.py`.
- Create: `docs/contracts/first-party-secret-rules-v1.json`, `tests/fpapi/test_secret_rules_contract.py`, `tests/fpapi/test_contract_fixtures.py`. 11종의 개별 응답 파일은 기존 fixture 생성 규칙을 따른다.
- 범위 밖: HTTP 동작 구현, 토큰 발급, FW9의 등록·HITL·사용자 동작 경로, 읽기 기준선 변경으로 파괴 변경을 숨기는 일.

**Interfaces / 공유:** 기본 편집·승격·연구·쓰기 참조와 `GET /v1/nodes/{id}/reviews` 계약을 제공한다. `history.versions[]`의 `actor`, `claimed_author`, `generated_by`, `payload_sha`, `data.write`의 단일 모양을 FW4/FW9가 소비한다. `secret_rules.version=fp-secret-rules-v1`, `sha`는 정규 JSON UTF-8 바이트로 계산하며 실제 값은 실행에서 산출한다. FW1은 스키마·벡터를 검증하고 실제 dry-run 무저장은 FW3/FW4에서 검증한다.

**출력 형식:** 계약 diff·fixture 목록·규칙 판/실제 해시·정적/계약 검사 종료 코드와 공통 인계 봉투.

**완료 기준:**

1. 만들기·편집·충돌·숨은 대상 404·tombstone·승격·비밀 거절·격리 저장·스풀 참조·연구 요청·연구 상태의 11종이 스키마 검증을 통과하고 읽기 경로 파괴 변경은 0이다.
2. 오류는 ADR 7.5의 코드·고정 문구이며 meta는 준비 전/후 모두 ADR 8.1의 단일 스키마로 검증된다. 미구현 경로를 준비 완료로 광고하지 않는다.
3. 합성 벡터가 식별자/내용 차이·다이제스트 예외·속성 이름·한글/보조 평면 문자·UTF-16 구간을 포함하고 공개 파일과 서버 규칙의 판·해시 대응을 검사한다. 실제 비밀·허용 목록은 없다.
4. `filter=label:prefix:`는 기존 `src/kb/read/nodes.py:463-480`의 분기를 근거로 fixture에서 동작을 확인한다. 실패하면 지원되는 대안을 계약에 명시한다.

### Task 3: FW3 — 쓰기 핵심·귀속·비밀 거절·멱등

**목적과 사용자 확인 결과:** 안전하지 않은 저장은 흔적 없이 거절하고 응답 유실·동시 편집에서도 한 초안을 한 기록으로 유지한다. 사용자는 충돌 응답, 재생 결과, 저장소 변화 0인 비밀 거절 시험으로 확인한다.

**목표:** ADR 2.3, 3.2, 3.4, 4.5~4.6, 5.1~5.6, 5.8, 7.1~7.4·7.7의 공통 쓰기 불변식을 구현한다.

**Files / 수정 범위:**

**Interfaces / 공유:** 기존 `author.resolve`, `put_record`, `tombstone_record`, `engine.commit`을 확장하며 기존 호출 인수의 호환성을 보존한다. HTTP 진입에는 서버가 정한 토큰 라벨·`change`·`on_secret`·대상 정책을 전달하고 클라이언트의 귀속 필드를 신뢰하지 않는다. FW4/FW6/FW9가 평면 `WriteResult`와 구조화된 `VersionConflict.current`를 소비한다. HTTP 실효 키는 `h\0<actor>\0K`, 만들기 ID는 ADR 5.1의 actor+키 해시다.

**출력 형식:** 변경 manifest·RED/GREEN 근거·실패 전후 원장/CAS/스풀 차이·오류/로그 무반향 증거와 공통 인계 봉투.

**완료 기준:**

1. 세 `change`의 귀속이 ADR 3.2와 일치하고 일반 HTTP `actor`는 사람이 아니다. 대상 확인·재생의 현재 가시성·판 확인·무연산·CAS 순서가 ADR 2.3과 일치한다.
2. 식별자 비밀은 격리 선택과 무관하게 422이며 NUL 키는 400이다. 경로 힌트는 400, 내용 비밀은 기본 422/명시 격리이며 거절·dry-run 뒤 원장 seq·CAS·스풀·보류·추출 큐·영속 캐시·로그에 입력 잔여가 0이다. 순번 진단과 코드포인트/UTF-16 구간이 합성 벡터와 같다.
3. 숨은 대상과 숨은 대상의 재생은 값·`current`·ID·판·`payload_sha`·seq가 없는 404다. tombstone은 마지막 put의 민감도/격리를 확인하고 보이는 dead `current`는 version/status만 준다. 낡은 판은 같은 내용이어도 409이고 복원 뒤 active다.
4. 다른 actor의 같은 키는 별도 기록이며 원장 meta 없이 ID를 재계산하고 세그먼트 복구 뒤 재생한다. 응답 유실 autosave→save 만들기는 같은 ID의 409+current이고 중복 기록은 없다. 기존 통로 전역 재생과 작성기 다이제스트 꼬리 예외는 유지된다.
5. 크기 제한·편집기 전용 정확한 위키 링크 모양이 적용된다. `TopicSpec`·`Review`·`change=auto`는 sLLM 큐에서 제외하고 Page/Note의 여러 판은 ID별 최신 참조 하나로 합쳐진다.

## 공백 해소 결과 (2026-11-05)

상세 근거와 미검증 항목은 [공백 해소안](2026-11-05-adr-0005-gap-resolutions.md)에 있다. 이 절은 결정만 요약한다.

- **G1 K-c 상한:** 사용자 승인. 연구 실행별 실제 LLM 요청·도구 실행 시도를 합산해 **30회**로 제한한다. 31번째 호출은 전송 전에 차단하고 `call_cap_exceeded`로 기록한다. 강제 검증(30/31 경계, 동시 예약, 재시도, 재시작, 불투명 어댑터 외부 호출 0)은 FW6에서 `tests/fpapi/test_research_call_cap.py`로 수행한다.
- **G2 WebAuthn:** 사용자 결정 없이 `webauthn==3.0.1`을 FW9의 기술 선택으로 둔다. 카운터는 `new_sign_count > stored_sign_count`를 KB가 별도로 요구한다. 설치와 lock 갱신, 실물 인증기 시험은 FW9 소유다.
- **G3 제공자 비용 대조:** 사용자 결정 없이 제공자별 능력을 `per_call` / `aggregate_only` / `unavailable`로 인계한다. OpenRouter는 generation ID 확보 시 `per_call` 후보, Anthropic·OpenAI는 `aggregate_only` 후보다. 관리자 키 발급은 이 계획 승인의 조건이 아니다. 호출별 대조가 안 되면 기간 합계, 차액 미반환, 7일 마감을 따른다.
- **G4 선행 인계:** 사용자 결정 없이 공통 인계 봉투와 task별 산출물·소비자 표를 채택한다. 순서는 FW1 → FW2 → FW3 → FW4 → FW5 → FW9 → FW6 → FW7 → FW8이다. TP1·TP5·E1·D5는 선행 task로 두고, 완료 증거가 확인되기 전에는 FW6 유료 경로를 열지 않는다.

**상태:** 검토 대기(사용자 계획 승인 필요). 유료 경로 개방, WebAuthn 실물 등록, FW7 통과, FW8 재시작 승인은 이 계획 승인과 별개다.
