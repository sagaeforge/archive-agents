# 요구사항 감사: 설계안 4건

- 작성일: 2026-10-31
- 역할: 요구사항 R1~R20 기준의 위반 감사다. 설계안의 우열은 판단하지 않는다.
- 성격: 시스템 설계 문서(CLAUDE.md 지침 5의 예외). 지식 데이터가 아니다.
- 대상: `proposal-simplicity.md`, `proposal-durability.md`, `proposal-retrieval.md`, `proposal-platform.md` 전문.
- 대조: `docs/research/` 보고서 9건, `docs/contracts/consumers/sagae-tools.md`, 1차 출처 3건, 감사 실측 4건(2장).
- 규칙: 애매하면 위반으로 판정했다. 그래서 건수가 많고, 무게는 등급으로 구분한다. 건수를 합산해 안을 비교하면 안 된다.
- 표기: `L292`는 해당 설계안의 줄 번호다. `A1`~`A4`는 이 감사의 실측이다. `D10`, `E7`, `P5`는 각 설계안의 실측 ID이고, 어느 안의 값인지 함께 적는다.

## 0. 요약

**그대로 구현하면 데이터를 잃는 결함은 1건이다.** Platform의 재구축 교체(PLT-01)다. 라이브 WAL DB에 `os.replace`를 쓰면 9회 시험 전부에서 확인 응답된 쓰기가 사라졌고 7회는 `integrity_check`도 실패했다(A1). 저널이 같은 파일에 있어 진실 계층까지 함께 잃는다.

**네 안 모두 충족을 증명하지 못한 요구는 R8과 R16이다.** 실제 WSL 재부팅 뒤 catch-up은 어느 안도 재지 않았고, 머신 밖 대상은 사용자 결정 전이라 디스크 장애에서 살아남는 경로가 아직 없다. 대조표에서 R16을 미충족으로 적은 안은 Retrieval뿐이다.

**구조를 바꿔야 하는 위반은 다음이다.**

| 안 | 내용 |
|---|---|
| Retrieval | first_party 진실이 그래프 DB 안에 있고 재구축 실측이 없다(R2). 노드에 버전 행이 없어 as-of가 과거 값을 재현하지 못한다(R4). 추출 호출에 턴 상한이 없다(R8) |
| Platform | 진실의 최근 구간이 그래프 DB 안에 있다(R2). `secret` 본문의 백업 경로가 없다(R16) |
| Durability | as-of 검색이 미구현, 미측정이다(R18). 시계열이 그래프 밖 silver 표에 있다(R3, R4) |
| Simplicity | 문서 전문 as-of를 지원하지 않는다(R18). 시계열이 그래프 밖이고 개요에서 사실 관계가 빠진다(R3) |

## 1. 판정 기준

| 등급 | 뜻 |
|---|---|
| 차단 | 문구대로 구현하면 확인 응답된 데이터가 사라진다. 고치기 전에는 채택할 수 없다 |
| 높음 | 요구 문구를 구조적으로 어긴다. 또는 요구의 핵심 동작에 증거가 없다. 설계 변경이나 선행 실측이 필요하다 |
| 중간 | 요구의 일부가 비었거나 근거가 어긋난다. 명세 보강으로 고칠 수 있다 |
| 낮음 | 문구 모순, 표기 불일치, 또는 애매해서 위반으로 판정한 항목이다 |

## 2. 감사 실측과 1차 출처

스크립트는 `/tmp/claude-1000/-home-sagae-sagae-knowloge-base/b32eef31-b09c-4e58-8902-431f279117b3/scratchpad/audit-req/scripts/`에 있고 tmpfs라 재부팅하면 사라진다. 사양은 아래 표로 다시 만들 수 있다. 값은 전부 공용 tmpfs 위이고 fsync 비용이 빠져 있다.

**A1. 라이브 WAL DB `os.replace`.** Python 3.13.18, SQLite 3.53.1. 쓰기 프로세스 4개가 `journal` 행과 합계 열을 한 트랜잭션에 쓰고 확인 응답을 파일에 남긴다. 1초 뒤 저널을 읽어 새 파일을 만들고 `os.replace`로 교체한다. 재생 시간 대용으로 0.2초 쉰다. Platform 14.5절에 꼬리 따라잡기 절차가 없어 넣지 않았다. 조건별 3회다.

| 쓰기 연결 | 확인 응답 | 유실 | `integrity_check` |
|---|---:|---:|---|
| 쓰기마다 새 연결 | 3,599~3,690 | 334~340 | ok 2회, 실패 1회 |
| 프로세스당 연결 유지 | 4,019~4,066 | 2,190~2,217 | 실패 3회 |
| 연결 유지, `flock` 게이트를 쥐고 교체 | 4,041~4,066 | 2,201~2,224 | 실패 3회 |

9회 전부 확인 응답된 쓰기가 사라졌고 오류를 낸 쓰기는 0건이었다. 게이트를 쥐고 교체해도 나아지지 않았다. 합계 열이 실제 행 수와 어긋난 회차도 있었다. 옛 `-wal` 프레임이 새 파일에 섞인 것으로 추정한다. Durability D10과 같은 방향이고, D10은 `integrity_check`가 ok였지만 A1은 쓰기 형태가 달라 9회 중 7회 실패했다.

**A2. rtk 상태 경로.** 가짜 HOME에서 `XDG_DATA_HOME`을 훅 프로세스에만 주고 `rtk hook claude`를 돌렸다. 출력의 `updatedInput.command`는 `rtk git status`였고 환경 변수 접두사가 없었다. 지정 경로에는 파일이 생기지 않았다. 그 명령을 같은 변수 없이 실행하자 `$HOME/.local/share/rtk/history.db`가 생겼다. 즉 훅 프로세스의 환경은 재작성된 명령에 전달되지 않는다.

**A3. 긴 읽기와 게이트 안 체크포인트.** 승격 프로세스가 `flock` 안에서 100행을 커밋하고 20배치마다 체크포인트를 돈다. 세션 쓰기는 50 ms 간격이다. 다른 프로세스가 읽기 트랜잭션을 0.25초 또는 3초 유지한다. `busy_timeout=30000`이다.

| 체크포인트 | 세션 쓰기 최대, 읽기 0.25초 | 세션 쓰기 최대, 읽기 3초 |
|---|---:|---:|
| 없음 | 0.2 ms | 61.7 ms |
| `PASSIVE` | 0.7 ms | 60.6 ms |
| `RESTART` | **281.1 ms** | **2,990.4 ms** |

`RESTART`는 읽기가 끝날 때까지 쓰기 잠금을 쥔 채 기다린다. 세션 쓰기의 정지 시간이 소비자 읽기 시간과 같아진다. p50은 어느 조건이든 0.1 ms다.

**A4. 표준 라이브러리 zstd.** 관리형 Python 3.13에서 `import compression.zstd`는 `ModuleNotFoundError`이고 3.14에서는 된다.

## 11. 감사 한계

- A1~A4는 공용 tmpfs 위의 짧은 시험이다. A1은 쓰기 4개, 교체 1회이고 재생 시간을 0.2초 대기로 대신했다. 방향 확인용이다.
- A3의 지연 값은 fsync가 없는 값이다. 읽기 시간과 쓰기 정지 시간의 관계만 읽어야 한다.
- 실제 WSL 재부팅, 전원 손실, 머신 밖 복원은 재지 않았다. 재부팅은 현재 세션을 끊는다.
- 다른 안의 실측은 재현하지 않고 문서로 대조했다. 다만 M5의 목적지는 남아 있는 스크립트로 확인했다.
- 실패 장면은 설계 문구대로 구현했을 때의 예상이다. A1, A2, A3, A4로 재현한 항목 외에는 실행하지 않았다.
- 세 안의 실측 절차에 지시 이탈이 있다. 설계 위반은 아니라서 등급을 매기지 않았다. Simplicity는 `~/.local/bin/python3.14` 링크를 약 1분 만들었다가 지웠고 부록 B에 적었다. Retrieval은 `~/.cache/kb-proposal-retrieval/`에 약 16 GB를 썼다가 지웠고 기존 venv를 재사용했다. Platform은 조사 작업의 venv를 읽기로 재사용했다.
- 이 감사의 부수 효과: scratchpad의 `audit-req/`에 스크립트와 결과 약 112 KB를 남겼다. rtk 시험은 가짜 HOME에서 했고, 전역 설정, crontab, systemd, 셸 프로필, `~/.local/bin`은 바꾸지 않았다. 저장소에는 이 문서만 추가했다.
