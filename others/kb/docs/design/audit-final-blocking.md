## 0. 결론

## 3. 결함

심각도 기준은 과제 지시를 따른다. blocker는 이대로 구축하면 실패하거나 지침을 어긴다. major는 큰 재작업이나 잘못된 결정을 부른다. minor는 고치면 좋다.

### 3.1 blocker

**BLK-01. 보관 중인 first_party가 어떤 백업 등급에도 없다.** (RULE-09와 같다)

- 위치: ADR L121, L142, L189, L269, L536, 계획 WP-13.
- 내용: T0는 "원장 전체, `raw/fp/`, 복원 비밀"이고 WP-13의 전송 대상은 "원장, 내보내기, raw/fp"다. `spool/fp-held/`, `spool/in/`, `inbox/`, `inbox/.done/`은 어떤 등급에도 없다 `[문서]`. `fp_open` 전에는 사용자 기록 전부가 여기에만 있다. 결정 3으로 `/mnt/c` 사본이 생겨도 이 경로만 빠진다. held 쓰기는 원장을 바꾸지 않으므로 `kb ship --if-dirty`도 깨우지 않는다 `[추론]`. PLT-03의 결함이 모든 first_party로 넓어진 형태이고, ADR 결정 1 "대체 불가능한 것은 파일 두 곳에만"과도 어긋난다.
- 수정: T0에 `spool/`, `inbox/`를 넣고 dirty 판정에 스풀 변경을 포함한다. `test_secret_path`, `test_drill`에 held 항목 복원을 넣는다. L121의 문장을 고친다.

**BLK-02. 체인이 이벤트 열을 다 묶지 않아 WP-01 인수 조건을 통과할 수 없다.**

- 위치: ADR L303, L1027, 계획 WP-01 `test_fault_injection`.
- 내용: 체인 입력에 `v`, `on_behalf_of`, `generated_by`, `subject`, `idem_key`가 없고 `record_head`, `meta`도 체인 밖이다. D8의 "해로운 미탐지 0"은 `event` 열이 적고 본문이 같은 행이던 Durability 프로토타입 값이라 ADR 구조로 옮겨지지 않는다.
- 근거: `[재현 R4]` 300회 중 19건이 체인과 `integrity_check`를 모두 통과했다. `e:record/f-0113`이 `e:record/f-0q13`이 돼도 잡히지 않는다. 인수 조건은 "미탐지 해로운 플립 0건"이다.
- 수정: 체인 입력에 이벤트의 모든 열을 넣는다. `record_head`, `meta`는 이벤트 재생으로 대조한다. `[재현 R5]` 해로운 미탐지 0건이다.

**BLK-03. 활성 소스 D18, D19가 `www.youtube.com`이다.** (FACT-01, RULE-05, PLAN-04와 같다)

- 위치: ADR L143, L679, L744, L745, L1201, 계획 WP-07, WP-21.
- 내용: D18은 `https://www.youtube.com/trends/`, D19는 `https://www.youtube.com/howyoutubeworks/recommendations/`다(인벤토리 주석). ADR은 둘을 활성으로 두는데 결정 1의 기본 동작은 "전부 꺼짐"이고, WP-21은 "YouTube에 요청하지 않는다"와 `test_hosts`의 `youtube.com` 0건을 요구한다. 구축하면 그 시험이 실패하거나 사용자 결정 전 경로를 호출한다. YouTube 약관 문구는 "access the Service using any automated means ... except (a) in the case of public search engines ... or (b) with YouTube's prior written permission"이다. ADR이 P05~P07을 끈 이유와 같은 조항이다.
- 수정: D18, D19를 초기 비활성으로 옮기고 `test_registry` 목록에 넣는다. D13(`blog.youtube`), D15, D22(`support.google.com`)는 robots 허용 경로이고 Google 약관 조항은 robots 위반 접근을 다루므로 같은 경우가 아니다. 다만 결정 1의 "전부 꺼짐" 문구와 맞게 사용자에게 명시한다.

**BLK-04. 게이트 효과 17/90이 시험 설계의 결과다.**

- 위치: ADR L69, L128, L722, L1216, 계획 WP-08 `test_distortion`, `gate2.py` L100.
- 내용: X6은 문장만 바꿨다. `gate2.py`는 `add("주어 교체", s.replace(a, b, 1), b)`로 바뀐 이름을 `subject` 자리에 넘겨서 주어 검사가 잡도록 만든다. ADR 10.6의 5단계는 주장의 `subject` 필드를 문맥과 대조할 뿐 문장이 그 주어를 말하는지 보지 않는다. 모델이 `subject`는 맞게 고르고 문장에 다른 이름을 쓰면 통과한다.
- 근거: `[재현 R2]` 필드를 유지하면 주어 교체 30/35 통과, 왜곡 45/90이다. 정직하게 구현하면 WP-08 기준 "20건 이하"를 넘고, 프로토타입을 베끼면 시험은 통과하지만 거짓 안심이 된다.
- 수정: 5단계에 "문장에 나온 등록 엔티티 별칭은 `subject` 별칭이거나 인용구·문맥에 있어야 한다"를 더한다. `[재현 R3]` 1/35, 16/90이고 원 주장 보류는 늘지 않았다. F7, 24장의 수치를 고치고 `test_distortion` 표본을 `subject` 유지로 정의한다.

**BLK-05. 시험 표본과 프로토타입이 세션 tmpfs에만 있다.** (PLAN-10과 같다. 그쪽은 major로 적었고, 이 문서는 복구 불가능성을 보고 blocker로 올렸다)

- 위치: ADR L59, L1287~1296, 계획 WP-05, WP-06, WP-08, WP-16.
- 내용: WP-08 `test_distortion`은 `proposal-retrieval/gate/out/gate_rows.json`의 49건과 문서 4건, `t5_tables.py`에 기댄다. WP-05 표기 공격 26건은 `tok_eval.py`에만 있고, 우회 15건과 프로토타입도 마찬가지다. ADR은 "사양으로 다시 만들 수 있다"고 적었지만 49건은 LLM 출력이고 재추출 일치율이 0.32~0.57이다(X10, R13). 경로도 세션별이라 다른 세션에서 열리지 않는다. 저장소에는 커밋이 하나도 없다.
- 수정: 재부팅 전에 `tests/golden/`, `docs/design/prototypes/` 같은 저장소 경로로 옮기고 WP 지시의 경로를 바꾼다.

### 3.2 major

**BLK-06. `eff_status`에 시간축이 없어 as-of가 현재 상태를 돌려준다.** (CTR-27의 추론을 재현했다)

- 위치: ADR L346, L362, L869, 계획 WP-02, WP-04, 계약 2.7, 2.9.
- 내용: `eff_status`는 `survival.verdict` 때 투영이 갱신하는 현재값이다. RET-02의 실패 장면이 주장 쪽에서 재발한다. `node`에는 이 열이 없어 표와 개요의 계산도 정해지지 않았다.
- 근거: `[재현 R6]` 판정 뒤 과거 시점 조회에서 그때 활성이던 주장이 사라진다. `test_asof`와 `test_eff_status`는 이 교차를 시험하지 않는다.
- 수정: 판정 때 `span`을 닫고 새 `span`을 열거나, as-of에서는 주어의 그 시점 버전을 조인해 계산한다. `visibility_sql`에 넣고 `test_asof`에 교차 사례를 더한다. 부하 시험에 as-of 개요를 넣어 감사의 해소 조건을 채운다.

**BLK-07. 상위 N 후처리가 필터 검색을 빈 결과로 만든다.** (CTR-13과 같다. 수치는 R7)

- 위치: ADR L68, 계획 WP-05, 계약 2.4, 4.8, 4.9.
- 내용: F6은 `sens`, `life`가 상수라 필터가 걸리지 않았고 재현율을 재지 않았다. DUR-01의 실패 장면이 명시한 "후처리 필터의 과소 반환"이 그대로 남았다. 1% 필터에서 질의의 21~30%가 있는 정보를 0건으로 답한다. 호출 모델은 이것을 "없는 정보"로 받아들인다. `page.total`과 `/v1/facets?q=`도 상위 N으로는 계산할 수 없다.
- 수정: 필터가 있으면 안쪽 `LIMIT`을 쓰지 않는다. `[재현 R7]` 38.4만 문단에서 p95가 210~270 ms에서 99~136 ms로 줄고 결과도 완전하다. N은 필터 없는 검색에만 둔다. `total`의 뜻을 계약에 확정하고 WP-05에 희귀 필터 재현율 시험을 넣는다.

**BLK-08. 앵커가 없으면 `seq` 되감기를 잡지 못한다.**

- 위치: ADR L123, L818, L1012, 계획 WP-13 `test_stale_backup`, 계약 4.12.
- 내용: `epoch`은 복원 때 머리가 앵커보다 뒤일 때만 오른다. 결정 2, 4 전에는 앵커가 `ledger/anchors.ndjson`뿐이고 복원본과 함께 낡는다. 12장의 앵커 불일치도 "머신 밖 설정 뒤"에 켜진다. `applied_seq > head`와 커서가 머리보다 앞선 경우의 규칙도 없다. 레드팀이 함께 제안한 "비정상 종료 시 `epoch`"은 빠졌고, fsync 도달은 미상이다(24장).
- 근거: `[재현 R8]` 새 쓰기가 gold에 0/5, 피드 0건, 오류 0이다. X4와 같은 장면이다. 전체 복원 런북은 `kb rebuild gold`를 돌리므로 gold 앞섬은 사라지지만 번호 재사용과 커서 앞섬은 남는다.
- 수정: 복원은 앵커 유무와 무관하게 항상 `epoch` + 1. tick 0단계에서 `applied_seq > head`면 투영을 멈추고 재구축한다. 커서가 `applied_seq`보다 크면 410이다. 로컬 앵커 대조는 머신 밖 설정 전에도 켠다.

**BLK-09. 투영 실패와 스풀 실패 경로에 규칙도 시험도 없다.**

- 위치: ADR L122, L508, 12장 실패표, 계획 WP-03.
- 내용: "투영 실패는 쓰기 실패가 아니다"의 근거 F4는 이 경로를 지나지 않는다. 프로토타입은 반대로 동작한다. `project_tail`은 seq 순서라 투영할 수 없는 이벤트 1건이 뒤 이벤트를 전부 막고 `kb rebuild`도 같은 곳에서 실패한다 `[추론]`. 12장에 투영 실패 행이 없고 `투영 지연`은 경고이며 DLQ는 파서용이다. `{spooled:true}`로 답한 쓰기가 재적재 때 `expected_version`이나 멱등 충돌로 거부되는 경우의 규칙도 없다. `projected`, `spooled`는 인수 조건에 한 번도 나오지 않는다.
- 근거: `[재현 R9]` 원장 4, gold 1에서 멈춘다.
- 수정: 투영 불가 이벤트의 처리를 정한다(격리 목록을 원장 이벤트로 남기고 건너뛰어 결정성을 지키거나, 멈추고 치명 경보). 스풀 재적재 실패는 DLQ와 사용자 알림으로 보낸다. 실패 주입 시험과 게이트 시간 초과 시험을 WP-03에 넣는다.

**BLK-10. 배치 100의 단위가 틀렸고 F3는 실제 투영을 재지 않았다.**

- 위치: ADR 0장 결정 4, L514, L515, 2장 F3, 계획 WP-03 `test_perf`.
- 내용: F3의 이벤트는 FTS 1행이다. 실제 문서 이벤트는 문단 수만큼 `unit`, `span`, FTS를 쓰고 이 작업이 게이트 안이다. 이벤트 수는 게이트 보유 시간을 묶지 못한다.
- 근거: `[재현 R10]` 이벤트당 5문단이면 p99 162.9 ms로 WP-03 상한 150 ms를 넘고, 부록 A의 쪽당 40문단이면 580.0 ms다. WP-03 시험은 작은 이벤트로 통과하므로 이 차이를 숨긴다.
- 수정: 상한을 게이트 보유당 투영 문단 수로 바꾼다. `[재현 R10]` 200문단이면 p99 108.7 ms, 80문단이면 41.5 ms다. `test_perf`를 실제 크기 이벤트로 정의한다. 대안으로 게이트 밖 비동기 투영도 비교한다.

**BLK-11. 계획의 재구축 순서가 지문을 게이트 안에서 계산한다.**

- 위치: ADR L87, 계획 WP-02 지시.
- 내용: WP-02 순서는 "게이트 획득 → 꼬리 따라잡기 → `wal_checkpoint(TRUNCATE)` → 지문 기록 → symlink 교체"다. 프로토타입 `rebuild()`에는 이 단계가 없어 F3의 4~87 ms는 지문을 뺀 값이다.
- 근거: `[재현 R11]` 72.2만 행에서 1.26초다. 실제 gold는 표가 14개이고 1년차 규모가 더 크므로 5초 쓰기 제한을 넘어 재구축마다 쓰기가 스풀로 갈 수 있다 `[추론]`.
- 수정: 지문은 교체 뒤 게이트 밖에서 같은 `applied_seq` 스냅샷으로 계산한다. 불일치면 경보하고 옛 빌드로 되돌린다. `test_swap_under_write`에 게이트 보유 상한을 넣는다.

**BLK-12. `record.redact`에 실행 주체가 없고 삭제 범위가 비어 있다.** (실행 명령 부재는 PLAN-31과 같다)

- 위치: ADR L132, L491, L1001, 계획 2.3, WP-01, WP-13 `test_redact_chain`.
- 내용: `kb redact` 명령과 소유 패키지가 없고 2.3 공개 함수에도 없다. ADR은 "git, restic까지 시험한다"고 적었지만 `test_redact_chain`에 git이 없고 봉인 세그먼트(`ledger/export`)도 없다. `inbox/.done/`, `spool/`, `ops/runs/`는 삭제 대상 목록에 없다. 시험은 로컬 restic뿐인데 제안된 대상 B는 `rest-server --append-only`라 `prune`이 막힌다(레드팀 2.8). 머신 밖 삭제는 미측정 그대로다. 내용 주소 저장이라 다른 레코드가 같은 객체를 쓰면 함께 지워진다 `[추론]`.
- 수정: 소유 패키지와 CLI를 정한다. 대상 목록에 위 경로를 넣고 세그먼트 재봉인과 MANIFEST 규칙을 적는다. 결정 2에 "append-only 대상의 삭제 절차"를 넣는다. `test_redact_chain`에 git, 내보내기, 공유 객체 사례를 더한다.

**BLK-13. T0와 T1의 시차 때문에 복원 뒤 재구축이 실패할 수 있다.** `[추론]`

- 위치: ADR L189, L190, L778, L1031, 계획 WP-13 `test_drill`.
- 내용: T0는 15분, T1은 1일이다. 재해 복원 때 원장은 `raw/objects`보다 최대 하루 앞서고, 그 구간의 표시 본문, 문단 색인, 시계열 묶음, LLM 원응답이 없다. gold는 원장 + CAS의 순수 함수인데 없는 객체를 만난 재구축의 규칙이 없다(`고아 객체 무시`는 반대 방향이다). `test_drill`은 한 세대를 통째로 복원하므로 이 상태를 만들지 않는다.
- 수정: 재구축이 없는 객체를 만나면 `gap.recorded`와 재수집 큐로 넘기고 계속한다. 또는 새 객체를 T0와 같은 박동으로 보낸다. T1이 하루 뒤인 복원 시험을 넣는다.

**BLK-14. 수집 에이전트가 가져온 본문을 읽을 수 없다.**

- 위치: ADR L54, L580, L921, L1129, 계획 WP-12, WP-17, WP-21.
- 내용: `kb-collector`의 도구는 `WebSearch`와 `kb-collect` MCP다. 프로필은 `kb_fetch`, `kb_ingest_*`, `kb_search`만 열고 `kb_source`가 없다. `kb fetch` 출력은 `{snapshot, text_sha, chars, status, policy}`다. `Read`와 `WebFetch` 제거는 맞지만 그 결과 에이전트가 본문을 볼 길이 없어 정확한 인용구를 낼 수 없다. WP-21 4단계가 `E_QUOTE_NOT_FOUND`로 막힌다 `[추론]`.
- 수정: 프로필에 `kb_source`를 넣거나 `kb_fetch` 출력에 예산 안의 본문을 정의한다. 이 프로필만으로 본문을 읽고 인용구를 제출하는 종단 시험을 WP-17에 둔다.

**BLK-15. `__new__` 주어의 처리가 정의되지 않았다.** (RULE-07이 생존 쪽을 다뤘다)

- 위치: ADR L413, L428, L723, 계획 WP-19.
- 내용: LLM이 모르는 주어를 고르면 `__new__` + 별칭 후보다. 그 뒤가 없다. LLM 주장 ID의 입력인 주어 id, `claim.subject NOT NULL`, 5단계 주어 문맥, G 단위 `liveness` 필수가 전부 풀리지 않는다. 1차 수집 초기에는 별칭 표가 비어 A~F 문서의 주어가 대부분 `__new__`가 된다 `[추론]`.
- 수정: 서버가 임시 엔티티를 만드는 규칙(키, 별칭, 상태, 5단계 대조 대상, 생존 입장)을 정하고 WP-19 시험을 둔다.

**BLK-16. LLM 주장 ID는 재추출에 안정하지 않다.**

- 위치: ADR L413, L445, L703, L710, 계획 WP-19.
- 내용: ADR은 "재추출과 문장 변화에 안정"이라 적었다. 주어가 완벽해도 인용구 일치가 0.32~0.57이다 `[재현 R13]`. 프롬프트나 모델을 바꾸면 캐시 키가 바뀌어 전 문단을 다시 추출하고 절반가량이 새 ID로 생긴다. LLM 주장은 자동 대체가 없고 인용구도 그대로라 재확인이 지우지 않으므로 활성 주장이 쌓인다 `[추론]`.
- 수정: 문구를 고친다. "같은 문단을 새 `extractor`로 다시 뽑으면 옛 `extractor` 주장을 `claim.retract`한다"를 규칙으로 두고 재추출 시험을 넣는다. LLM 주장 자동 대체 금지 시험도 함께 둔다.

**BLK-17. Markdown 경로에 숨김 제거가 없다.**

- 위치: ADR L730, 계획 WP-07 지시, `test_hidden`.
- 내용: "이미 NFC 텍스트나 Markdown이면 그대로 쓴다"이고 숨김 제거는 HTML에만 있다. G1, G2의 `.md` 문서와 CHANGELOG가 이 경로다. HTML 주석과 인라인 숨김이 표시 본문에 남아 인용구 근거가 되고 L2 입력이 된다. "사람이 볼 수 없는 문장이 인용구 근거가 되지 않는다"가 활성 소스 다수에서 성립하지 않는다 `[문서]`. 표시 본문은 재계산하지 않으므로 첫 수집 뒤에는 고치기 어렵다.
- 수정: passthrough 앞에 HTML 주석과 인라인 숨김 제거를 넣고 `test_hidden`에 Markdown 사례를 더한다. 외부 스타일시트 숨김은 잡지 못한다는 한계를 24장에 적는다.

**BLK-18. `kb_put` 외부 경로에 입력과 시험이 없다.**

- 위치: ADR L135, L528, 계약 6.1, 계획 WP-03, WP-12.
- 내용: 3장 검증 칸은 WP-03인데 WP-03 지시와 인수 조건에 `source_url`이 없고, 게이트는 WP-08이라 순서상 시험할 수도 없다. 입력은 `record.source_url`, `record.quote`뿐이고 게이트가 요구하는 `subject`, `statement`, `kind`, `stance`, `method`가 어디서 오는지 없다.
- 수정: 입력 필드를 계약에 넣거나, 외부 사실은 `kb_request` 티켓으로 돌리고 `kb_put`에서 뺀다. WP-12에 시험을 둔다.

**BLK-19. `ttl30` 삭제를 실행하는 작업이 없다.** (RULE-10이 같은 L686 문구를 다룬다)

- 위치: ADR L193, L488, L686, 11장 내부 작업 표.
- 내용: Data API 응답은 30일 뒤 지운다고 적었지만 내부 작업 표와 어느 패키지에도 실행자가 없다. L686은 "키가 생기면 소스 파일의 `enabled`만 켠다. 코드 변경 없음"이다. 그대로 켜면 30일 보존 정책(인벤토리 III.E.4)을 넘긴다 `[추론]`.
- 수정: `ttl_sweep` 내부 작업과 시험을 소유 패키지에 넣고 L686 문구에서 Data API를 뺀다.

## 6. 통과한 항목

- `safe_fetch`의 15개 우회 차단과 실제 URL 4건이 재현됐다. 핵심 구조(주소 고정, 홉마다 재검사, 크기 상한)에 결함을 찾지 못했다.
- `RESTART` 규칙은 쓰기 정지를 약 100 ms로 묶는다(R12). 상한이 없으면 5초다.
- 낡은 전제 주석의 처리는 규칙과 시험이 있고 미측정 항목을 문서가 밝혔다.
- COM-02, COM-03, COM-04의 미해소 서술은 정직하다. 사용자 결정 7건과 대응한다.
