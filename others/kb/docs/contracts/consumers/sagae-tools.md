# sagae-tools 소비자 요구사항

- 상태: 잠정안(2026-10-31 수신). 도구 조사 전 요구사항이며 스택과 수치는 바뀔 수 있다. sagae-tools가 조사와 설계를 마치면 확정본을 보낸다.
- 출처: `sagae-tools-0e` 세션 회신. ADR과 충돌하는 항목은 그 세션에 알린다.
- 도구: KB를 조회해서 가시화하는 도구. 이름 미정, sagae-tools는 아직 빈 저장소다.

## 런타임

- 로컬 우선 웹앱. 브라우저 UI에 얇은 로컬 백엔드를 붙인다. 서버 런타임은 TypeScript + Node 26이다(2026-10-31 정정, 이전 회신의 Bun을 대체). 데스크톱 앱이나 터미널 UI는 아니다.
- 정정 이유: 관제 서버는 systemd 소켓 활성화로 시작한다. Bun은 전달받은 fd를 무시했고 Node 26은 `listen({fd:3})`로 동작했다(sagae-tools 재현).
- KB 영향: 없다. 게이트웨이 안 라이브러리 전제는 철회됐고 KB는 라이브러리를 내지 않는다(계약 1장).
- WSL2 머신에서 돌리고 나중에 Proxmox로 옮길 수 있다. KB가 로컬이든 원격이든 도구를 고치지 않아도 되는 경계를 원한다.

## 접근 방식

| 순위 | 방식 | 용도와 이유 |
|---|---|---|
| 1 | 버전이 붙은 HTTP 읽기 API(JSON, `/v1`) | 저장 스키마 변경과 분리되고, 로컬과 원격에서 똑같이 쓰며, 스키마에서 TS 타입을 생성할 수 있다 |
| 보조 | 스냅샷 export | 그래프 개요 일괄 로드, fixture 생성 |
| 대안 | 같은 JSON 계약을 내는 CLI 또는 라이브러리 | HTTP 데몬을 두기 어려운 경우 수용 |

- MCP는 에이전트용으로 보고 UI 데이터 경로로 쓰지 않는다. HTTP와 조회 코어를 공유하면 좋다.
- 읽기 전용 DB 파일 직접 접근은 원하지 않는다. 설계가 바뀌는 동안 저장 구조에 묶이기 때문이다.

### HTTP 제공 방식 선택지: sagae-tools 독립 관제 서버

`sagae-tools`가 사용자 요청으로 MCP 서버들과 함께 관제 서버(게이트웨이)를 설계하기 시작했다. 조사 초기 단계이며 확정이 아니다. 결정은 KB ADR에서 한다.

- 성격: 뷰어 부속이 아니라 독립 서버다. 뷰어 없이 동작하고, 뷰어는 소비자 중 하나다.
- 사용자 의향(`sagae-tools` 세션 전달): 뷰어에 종속되는 형태를 원하지 않고, MCP 서버들을 Claude Code 확장에 직접 넣기보다 관제 서버 하나에 위임하는 쪽을 선호한다.
- KB 영향: KB의 MCP를 플러그인이나 사용자 범위에 직접 넣는 대신 관제 서버에 등록하는 안을 ADR 선택지에 포함한다. 실제 적용 여부는 KB 세션이 사용자에게 확인한다.

- 확정(2026-10-31 정정): 관제 서버 tower는 KB HTTP를 쓰지 않고 KB MCP만 stdio 자식으로 띄운다. HTTP 소비자는 `loupe serve`(Node 26, 같은 사용자)이고 Unix 소켓을 쓴다. 게이트웨이 안 라이브러리 안은 sagae-tools 설계에서도 버렸다(sagae-tools의 `docs/design/tower.md`, `docs/design/loupe.md`, `docs/adr/0001-architecture.md`).

## 규모와 지연

측정값이 아닌 목표치다.

- 개요 약 1만 노드·5만 엣지, 이웃 확장 1회 약 200노드
- 상세·이웃·검색 p95 200ms 이내, 개요 일괄 로드 2초 이내
- 실시간 푸시는 필요 없다. 변경 피드를 30~60초 간격으로 폴링한다. 사용자는 한 명이다.

## 쓰기

- 도구는 읽기 전용이다.
- first_party 입력 창구는 이 도구에 기대지 않고 KB 쪽에서 설계한다.
- 나중에 쓰기가 필요해지면 KB 쓰기 API를 통해서만 하며, 그때 별도로 협의한다.

## 집계

- KB 제공: 필터 적용 상태의 개수·분포, 시간 구간별 개수. 클라이언트가 전체 데이터를 들고 있지 않기 때문이다.
- 도구 계산: 레이아웃, 커뮤니티 탐지, 중심성 같은 시각화용 파생값.
- 점수와 추천은 요구하지 않는다.

## 계약 관리

- 계약 원본은 KB 저장소 `docs/contracts/`에 둔다.
- 형식은 OpenAPI 3.1 + JSON Schema를 제안받았다.
- fixture도 계약과 함께 KB가 소유한다. 대체 체인, 유효·관측 시점이 어긋나는 소급 정정, dead 상태, 병합된 엔티티, 한글 본문, 인용구 위치를 포함한다.
- 양쪽이 계약 테스트를 돌린다. KB는 응답을 스키마로 검증하고, 도구는 fixture로 검증한다.
- 호환이 깨지는 변경은 major 버전을 올리고 sagae-tools 세션에 알린다.

## 계약에 반영할 요청

- 엔티티·관계·주장·출처 스냅샷에 불변 ID를 두고, 병합 시 `merged_into`로 잇는다. 딥링크가 깨지지 않아야 한다.
- 페이지네이션은 커서 방식으로 한다.

## 추가 계약 요구

2026-10-31 추가 회신. 9건 모두 계약 문서에서 다룬다.

1. 민감도: `sensitivity` 필드와 기본 숨김 규칙. first_party가 같은 그래프에 들어가므로 읽기 기본값에서 무엇이 빠지는지 명시한다. superseded와 dead의 기본 제외 규칙도 함께 정한다.
2. 인용 위치: 오프셋 기준은 토큰화된 색인 텍스트가 아니라 표시용 본문이다. 단위를 명시한다(Python 코드포인트와 JS UTF-16은 값이 다르다). 제안은 코드포인트 오프셋과 W3C TextQuoteSelector(exact, prefix, suffix) 병기다.
3. 개요 응답: total, truncated, 안정된 정렬, 필수 필터를 정의한다. 1만 노드·5만 엣지는 목표치이며 실제 규모 예측은 아직 없다.
4. 전체 그래프 입력: 도구가 중심성과 커뮤니티를 계산하려면 전체 노드와 엣지가 필요하다. 스냅샷 export를 그 입력으로 지정하고 형식을 정의한다.
5. 공통 봉투: `schema_version`, `data_as_of`, build ID. 재빌드와 게시 중의 읽기 동작, 조건부 GET, 오류 형식(RFC 9457 제안), 단일 타임스탬프 형식(RFC 3339 UTC 제안)을 정한다.
6. 읽기와 적재 격리: 읽기가 적재를 막으면 안 된다. sagae-tools 측 재현 결과: DuckDB 2.0.0 읽기 전용 연결이 쓰기를 막고, SQLite WAL은 `mode=ro`에서도 `-shm`, `-wal` 파일을 만들며 읽기 전용 디렉터리에서 실패한다. KB 실측으로 재확인한다. 파일 방식 대체 경로를 둔다면 게시된 사본을 읽게 한다.
7. 한국어 검색: KB 안에서 제공한다. sagae-tools 측 재현 결과: 일반 SQLite trigram은 '채널', '광고' 같은 두 글자 단어에서 0건이었다. 도구 쪽에서 대신 구현하지 않는다.
8. HTTP를 연다면: Host 헤더 검사, 와일드카드 CORS 금지, 인증을 넣을 자리.
9. first_party 표시: 본문 형식, 작성자, 버전, 노트 간 링크. 백링크와 Notion식 페이지가 가능한지가 여기서 갈린다. 수집 신선도, 실행 지표, 요청 큐를 읽기 범위에 넣을지도 정한다.

## KB ADR 참고 실측

2026-10-31 추가 회신. 모두 sagae-tools 측 실측이며 KB가 재현한 값이 아니다. 관제 서버의 병합 방식은 아직 사용자 결정 전이다.

1. 언어 제약: 시험한 병합 구성에서 실제 Python SDK stdio 서버가 자식 프로세스 하나로 안정 동작했다(호출 2~4ms).
2. `resource_link` 의존 금지: 기성 게이트웨이 4종 모두 리소스 URI만 바꾸고 `resource_link`는 그대로 둬서 도구 결과의 링크를 다시 읽지 못했다. 스냅샷 본문은 id로 읽는 도구로 제공한다.
3. 리소스 URI 스킴: `kb://` 같은 고유 스킴을 쓴다. URI가 겹치면 시험 구성이 다른 서버의 본문을 돌려줬다.
4. 기동 속도: 시작이 늦으면 Claude Code가 5초 버전 탐색에 실패해 구버전 프로토콜로 떨어지고, 그 세션은 알림 스트림이 없다.
5. 동기 쿼리 격리: 메인 스레드의 200ms 동기 처리가 MCP와 SSE를 완전히 멈췄고 워커로 옮기면 해소됐다. KB는 프로세스 안 라이브러리를 내지 않으므로 KB의 MCP 서버와 HTTP 서버 내부 설계에만 적용한다.

## sagae-tools가 답을 기다리는 질문

1. 예상 규모(엔티티, 주장, 스냅샷 수). 1만 노드 가정의 확인용이다.
2. KB 실행 위치(로컬 또는 Proxmox)와 HTTP 데몬 가능 여부.
3. 출처 스냅샷 본문 형식(HTML, Markdown, 텍스트).
4. KB 구현 언어와 동시 읽기 안전성. 게이트웨이 안 호출 전제는 철회됐다.

답은 계약 12장에 있다.

## 계약 v0 1차 회신

2026-10-31 sagae-tools 세션 회신. 계약 13장 9건 중 2건에 동의했고 나머지는 재측정과 대조 뒤 회신한다.

- 경로: Unix 소켓 기본에 동의한다. TCP 8737은 v1에서 쓰지 않고 Proxmox 이전 때의 보조 경로로 둘 수 있다.
- 토큰: 소켓 경로에는 토큰이 없다. TCP와 원격 경로는 파일 + `Authorization: Bearer`이고, 파일은 mode 600으로 한다.
- 개요 기본 타입: 미정. 추정 2만~5만 노드가 sagae-tools 측정(1만 노드, 5.1만 엣지)을 넘어 다시 재는 중이다.
- 요청: `docs/contracts/openapi.yaml` 초안을 WP-10 구현 전에 제공한다. loupe가 여기서 타입을 생성한다. 없으면 sagae-tools에 수기 사본이 하나 더 생긴다.

## 계약 v0 2차 회신

2026-10-31 sagae-tools 세션 회신. 계약 13장 9건의 답, 채울 공백 20건, 남은 요청 6건, 닫은 항목을 담았다. 원문은 `docs/contracts/consumers/sagae-tools-reply-2.md`다. 측정값은 sagae-tools 측 값이다. 공백 16~20은 KB의 답을 기다린다.

## 다음 문서 수정 때 처리할 요청

2026-11-01 sagae-tools 세션 회신. loupe는 `openapi.yaml` 0.3.1 기준으로 옮겼고 kb-mock으로 시험한다. 둘 다 동작을 막지 않는다.

1. `as_of_valid`: `openapi.yaml`은 제약 없는 문자열이라 빈 값도 스키마상 유효하고, 산문은 RFC 3339 또는 날짜라고 한다. `format`이나 `pattern`으로 맞춘다.
2. `/v1/facets`의 `q`: `openapi.yaml`은 필수, 산문 4.9는 "q가 있으면"이다. 어느 쪽인지 정한다. loupe는 지금 항상 보낸다.
3. KB 측 요청: 계약 12장 예상 주장 규모를 29만~37만으로 갱신한다(측정 창당 7.2~9.53, ADR 부록 A). 현재 값은 10만~30만(창당 4건 추정)이다. 동작을 막지 않는다.
