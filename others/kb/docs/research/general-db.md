## 0. 요약

**범용화는 저장 계층 1위를 바꾸지 않고, 2위 이하의 구도를 바꾼다.**

- **SQLite WAL은 1위를 유지하고 격차가 벌어진다.** 시험한 임베디드 엔진 5종 중 기본 설정에서 두 번째 쓰기 프로세스를 받은 것은 SQLite뿐이다. LadybugDB(`enable_multi_writes` 포함), Grafeo, DuckDB, Turso는 잠금으로 거부했다 [M3]. 범용 DB는 세션, CLI, 파일 입력, 타이머가 모두 쓰므로 이 차이가 곧 지원 여부다.
- **새 2위 후보는 임베디드 PostgreSQL이다.** `graph-store.md`에서는 AGE가 없어 제외됐지만, 사용자 레코드에는 그래프 확장이 필요 없다. sudo 없이 pip 휠로 17.9가 뜨고, 16 작성자에서 1,703쌍/s(p99 12 ms)로 SQLite의 6.6배다. 유휴 PSS 15.6 MB, 콜드 스타트 약 215 ms다 [M4]. 다만 이 처리량은 이 조사가 가정한 세션 부하(8세션 합계 약 17쌍/s)의 100배이고, 서버 프로세스, 커서 피드의 커밋 순서 문제, 단일 파일 백업 상실을 대가로 치른다. 전환 조건을 정해 두고 보류하는 쪽이 근거에 맞는다.
- **LadybugDB와 FalkorDB는 주 저장소 후보에서 내려간다.** LadybugDB 읽기 투영(선택지 2)은 재구축 가능한 층이라 그대로 유효하다.
- **소비자 목표는 쓰기 중에도 크게 남는다.** 1만 노드·5만 엣지에서 쓰기 작업 중 HTTP p95는 상세 2.5 ms, 이웃 14.7 ms, 검색 6.2 ms이고 개요는 최대 387 ms였다. 20배 규모(20만·100만)에서도 상세 6.7 ms, 이웃 36 ms, 검색 85 ms다 [M6][M7].
- **상시 프로세스 없이 HTTP를 제공할 수 있다.** 실제 systemd `.socket`으로 첫 응답 p50 150 ms(최대 169 ms), 웜 p50 2.3 ms, 유휴 메모리 0을 쟀다 [M9]. 콜드 응답도 p95 200 ms 목표 안이다.
- **그 경로에 함정이 하나 있다.** 기본 시작 제한(10초 5회)을 넘기면 서비스뿐 아니라 소켓 유닛까지 `failed`가 되어 수신을 멈춘다. `StartLimitIntervalSec=0`으로 해결했다 [M9].
- **호출마다 프로세스를 띄우는 CLI도 된다.** 표준 라이브러리만 쓰면 p95 25~42 ms다 [M8]. `sagae-tools.md`의 "p95 200ms를 맞추기 어려울 수 있다"는 우려는 읽기 경로에 Kiwi나 FastMCP를 올리지 않는 한 해당하지 않는다.
- **공유할 것은 프로세스가 아니라 코드다.** MCP와 HTTP를 같은 코어로 묶자 같은 스냅샷에서 응답이 일치했다 [M10]. 그러나 한 프로세스에 합치면 콜드 스타트가 111 ms에서 537 ms로, PSS가 38 MB에서 89 MB로 는다 [M9].
- **백업에서 가장 큰 사실은 이 PC의 물리 디스크가 1개라는 점이다.** `ext4.vhdx`도 C:에 있어 `/mnt/c` 사본은 디스크 장애를 막지 못한다 [M24]. 머신 밖 사본만 그 장애를 막는다. 이번 조사에서 머신 밖 복원은 자격 증명이 없어 재지 못했다.
- **SQLite 스냅샷을 restic에 넣을 때는 백업 API가 낫다.** 같은 변경량에 세대당 저장소 증가가 `VACUUM INTO` 20~25 MB, 백업 API 5~6 MB였다 [M21].
- **측정 한계:** DB는 공용 tmpfs에 뒀다. fsync 비용은 실제 ext4에서 잰 값(append p50 약 1.2 ms)을 주입해 모사했고, 전원 손실과 콜드 페이지 캐시는 재지 않았다.

### 1.3 fsync 비용을 다룬 방법

`graph-store.md`의 미해결 1번은 ext4 fsync 지연이다. tmpfs에서는 fsync가 공짜라 재지 못했다. 임시 파일은 scratchpad에 둬야 하고 저장소에서 쓸 수 있는 파일은 이 보고서뿐이므로, **이 보고서 경로 하나를 프로브로 썼다**. 4 KB를 쓰고 동기화하기를 300회씩 3번 돌린 뒤 파일을 지웠다. 저장소에 잔여물은 없다 [M0].

| 동작 | p50 | p95 | p99 | 최대 |
|---|---:|---:|---:|---:|
| append + fdatasync | 1.22~1.30 ms | 1.51~1.88 ms | 2.13~3.79 ms | 7.19 ms |
| append + fsync | 1.16~1.20 ms | 1.45~1.48 ms | 2.14~2.87 ms | 7.39 ms |
| 덮어쓰기 + fdatasync | 0.42~0.44 ms | 0.49~0.52 ms | 0.51~0.58 ms | 0.89 ms |

이 값을 바탕으로 `LD_PRELOAD` 심(`fsync_delay.c`)이 `fsync`, `fdatasync`마다 1.3 ms를 더하게 했다. 표의 `L=1.3`이 이 조건이다. 민감도 확인으로 5 ms, 20 ms도 돌렸다. 이 측정의 한계는 분명하다. fsync 호출 지연만 모사하므로 ext4 저널 경합이나 페이지 캐시 효과는 들어가지 않는다.

### 2.2 스키마 없는 레코드와 타입 확장

20만 레코드에서 세 방식을 비교했다 [M12].

| 항목 | JSON 텍스트 | JSONB | EAV |
|---|---:|---:|---:|
| 적재 | 139 ms | 208 ms | 1,813 ms |
| 표 크기 | 30.3 MB | 22.7 MB | 33.6 MB(+색인 29.6 MB) |
| 전체 스캔 필터 | 62.9 ms | 20.6 ms | 해당 없음 |
| 단일 키 조회 | 색인 시 p50 0.01 ms | 색인 시 p50 0.01 ms | p50 0.11 ms |
| 두 키 교집합 | 해당 없음 | p50 0.04 ms | p50 7.16 ms |

JSONB 문서는 텍스트 JSON보다 "less than half the number of CPU cycles"로 처리되고 5~10% 작다고 적는다 [S4]. 내 측정은 3배 빠르고 25% 작았다. 다만 텍스트 쪽은 `json.dumps` 기본 구분자(공백 포함)라 크기 차이가 부풀려졌다. 형식은 이후 버전과 호환되도록 설계됐다고 한다 [S4]. 다만 바이트를 직접 읽지 말고 JSON 함수로 다뤄야 한다 [S4].

**타입 확장은 재작성 없이 된다.** 자주 쓰는 속성만 승격하면 된다.

| 동작(20만 행) | 시간 | 추가 크기 |
|---|---:|---:|
| `ADD COLUMN ... GENERATED ALWAYS AS (...) VIRTUAL` | 0.14 ms | 0 |
| 생성 열 색인 구축 | 99.6 ms | 3.3 MB |
| 표현식 색인 구축 | 77.6 ms | 2.4 MB |
| 부분 색인 구축(`lang='ko'`) | 28.9 ms | 0.8 MB |

`ALTER TABLE`로는 VIRTUAL 열만 추가할 수 있다 [S5]. 색인이 있으면 조회 p50은 0.01 ms다.

타입 정의는 `type_def` 표에 JSON Schema 2020-12로 둔다. `additionalProperties: true`를 기본으로 하면 스키마에 없는 속성도 받으면서 아는 속성은 검증한다. 검증 비용은 레코드당 `jsonschema` 14.4 µs, `fastjsonschema` 0.6 µs(컴파일 1.13 ms)다 [M13]. 쓰기 경로에서 무시할 수준이다. 2020-12는 JSON Schema의 현행 버전이고 [S27] OpenAPI 3.1, 3.2와 MCP의 기본 방언이다 [S26][S28]. 타입 정의 하나를 저장소, HTTP 계약, MCP 도구가 함께 쓸 수 있다.

### 2.3 프로토타입 스키마

대외 수집과 사용자 생산을 같은 그래프에 둔다(CLAUDE.md 저장 범위). 관계와 주장은 불변 ID를 가진 1급 행이다.

```sql
CREATE TABLE node(rid INTEGER PRIMARY KEY, id TEXT NOT NULL UNIQUE, type TEXT NOT NULL, origin TEXT NOT NULL,
  status TEXT NOT NULL, sensitivity INT NOT NULL, label TEXT NOT NULL, body TEXT, body_format TEXT, props BLOB,
  author TEXT, merged_into TEXT, version INT NOT NULL DEFAULT 1, content_sha TEXT, created_at INT, updated_at INT);
CREATE TABLE node_version(rid INT, version INT, status TEXT, label TEXT, body TEXT, props BLOB, author TEXT,
  valid_from INT, valid_to INT, recorded_at INT, expired_at INT, change_note TEXT, PRIMARY KEY(rid, version)) WITHOUT ROWID;
CREATE TABLE edge(rid INTEGER PRIMARY KEY, id TEXT UNIQUE, src INT, dst INT, rtype TEXT, weight REAL, source_url TEXT,
  sensitivity INT, author TEXT, valid_from INT, valid_to INT, recorded_at INT, expired_at INT);
CREATE TABLE change_log(seq INTEGER PRIMARY KEY AUTOINCREMENT, at INT, op TEXT, kind TEXT, id TEXT, version INT);
CREATE TABLE idem(key TEXT PRIMARY KEY, response TEXT, at INT) WITHOUT ROWID;
CREATE VIRTUAL TABLE fts USING fts5(tok, content='', contentless_delete=1, tokenize="unicode61 remove_diacritics 0");
```

| 산출물 | 표현 |
|---|---|
| 노트 | `type=Note`, `body_format=markdown`. `[[...]]`는 엣지(`LINKS_TO`)로 분해한다 |
| 결정 | `type=Decision`, `props`에 MADR 필드. 대체는 `status`와 대체 엣지로 표현한다 |
| 프로젝트 산출물 | `type=Artifact`, `props.project`, `props.uri`, `content_sha`. 큰 바이너리는 DB 밖에 두고 해시로 잇는다 |
| 백링크 | `edge(dst, rtype)` 색인으로 조회. 별도 저장 없음 |

공개 ID는 불변 문자열이고 병합은 `merged_into`로 잇는다. 새 레코드에는 시간 정렬되는 UUIDv7 [S21]을 쓸 수 있다. 프로토타입은 임의 문자열이다.

Notion식 페이지(속성 + 본문 + 백링크)는 이 모델로 된다. 블록 단위 ID와 블록 링크는 안 된다. 필요하면 블록 표를 더해야 하며 이번에 재지 않았다.

### 2.4 버전 이력, 작성자, 민감도

**버전 이력.** `node`는 현재 상태이고 `node_version`은 추가 전용이다. 수정은 옛 행의 `expired_at`을 닫고 새 행을 넣는다. 8개 프로세스가 한 레코드를 1,600회 고친 시험에서 버전 행 1,601개, 유실 0건이었다 [M15]. 전체 복사 방식이지만 비용은 작다. 하루 노트 10개를 5번씩 고쳐 5년이면 약 9만 버전이고, 건당 2 KB면 약 180 MB다(계산값).

**작성자 귀속.** CLAUDE.md는 사용자의 판단을 사용자를 작성자로 명시해 저장하라고 정한다. 세션이 대신 쓴 경우까지 구분하려면 한 칸으로는 부족하다. W3C PROV의 구분을 그대로 쓸 수 있다 [S24].

| 필드 | PROV 대응 | 예 |
|---|---|---|
| `author` | `prov:wasAttributedTo` | `user:sagae`, `agent:session-a` |
| `generated_by` | `prov:wasGeneratedBy` | 세션 ID, 도구 실행 ID |
| `on_behalf_of` | `prov:actedOnBehalfOf` | `user:sagae` |
| 이전 버전 링크 | `prov:wasRevisionOf` | `(rid, version-1)` |

프로토타입은 `author`만 구현했다. 나머지는 재지 않았다.

**민감도.** 4단계 `public`, `internal`, `private`, `secret`을 정수로 저장하고 모든 조회가 `sensitivity <= max`로 거른다. 표준 어휘가 필요하면 TLP 2.0의 CLEAR, GREEN, AMBER, RED 구분을 쓸 수 있다 [S25]. 단 TLP는 공유 범위 규약이지 접근 제어가 아니다.

- 숨겨진 레코드는 없는 레코드와 같은 404로 답한다. 존재 여부도 새지 않는다 [M6].
- 검색, 패싯, 개요, 이웃이 같은 필터를 거친다. 공용 코어 하나를 통과시키는 이유다.
- 프로토타입의 `max_sensitivity` 쿼리 파라미터는 인증 없이 받는다. **계약에서는 토큰 범위에 묶어야 한다.** 지금 형태로는 뷰어가 `secret`을 요청할 수 있다.
- SQLite에는 행 수준 보안이 없다. 격리는 코어 코드에 달려 있다.

### 2.5 진실의 원천을 어디에 둘 것인가

사용자 생산 정보는 대체 불가다. 수집 정보는 WARC에서 재구축되지만(`etl-orchestration.md` M14) 노트와 결정은 그렇지 않다.

| | DB가 원본, 파일은 입력·내보내기 | Markdown이 원본, DB는 색인 |
|---|---|---|
| MCP 쓰기 원자성 | 한 트랜잭션 | 파일과 DB 이중 쓰기 |
| 버전 이력, as-of | DB 내장 | git에 의존, 트랜잭션 시간 없음 |
| 사람 편집 | 입력 폴더 + 충돌 기록 [M16] | 자연스럽다 |
| 재구축 | 백업에서 복원 | 파일에서 재색인 |
| 사람이 읽는 백업 | 결정적 내보내기 [M23] | 그 자체 |

근거로는 왼쪽이 유리하다. 쓰기 통로가 여럿이고 as-of가 계약 요구이기 때문이다. 대신 내보낸 파일을 사람이 고쳤을 때의 흐름을 3.3절처럼 명시해야 한다.

## 3. 쓰기 경로

### 3.1 공용 쓰기 코어

모든 통로가 함수 하나를 부른다. `BEGIN IMMEDIATE`, 멱등 키 확인, 현재 버전 확인, 내용 해시 비교, 버전 행과 FTS 갱신, 멱등 키 저장, 커밋 순서다. 약 60줄이다. 재현 코드는 11장에 있다.

| 요소 | 동작 | 근거 |
|---|---|---|
| 멱등 키 | 같은 키의 재시도는 첫 응답을 돌려준다 | 8개 프로세스 동시 호출에서 생성 1, 재생 7, 버전 1 [M15] |
| 낙관적 잠금 | `expected_version`이 다르면 충돌 | 1,600회 수정, 충돌 재시도 10회, 유실 0건 [M15] |
| 내용 해시 | 같은 내용은 새 버전을 만들지 않는다 | 파일 재적재 무변경 [M16] |
| 크래시 | 응답 전에 죽어도 재시도가 안전하다 | SIGKILL 3회, 키 수 일치, 커밋 후 미응답 1건이 재생으로 복구 [M15] |

`Idempotency-Key` 헤더는 IETF 초안 -08이 진행 중이다(2026-10-22 갱신, 2027-04-25 만료, Standards Track 지향). 재시도는 일관된 응답, 진행 중 재시도는 409, 다른 본문의 재사용은 422를 권한다 [S22]. 지금 있는 쓰기 도구는 인자 이름만 맞춰 두면 HTTP 쓰기 API를 열 때 그대로 옮길 수 있다.

### 3.2 MCP 쓰기 도구

FastMCP 4.1.4로 같은 코어를 노출했다 [M10].

- 같은 키 재시도는 `{"id":"note-1","version":1,"replayed":true}`를 돌려줬다.
- 낡은 버전 기반 수정은 `{"error":"version_conflict","detail":"expected 1, found 2"}`다.
- 이력에 `(1, agent:session-a)`, `(2, agent:session-b)`가 남았다.
- 도구 주석 `readOnlyHint`, `idempotentHint`, `destructiveHint`가 `tools/list`에 실렸다. 스키마상 이 값은 힌트이고 신뢰할 수 없는 서버의 값은 믿으면 안 된다 [S28][S30]. 서버 쪽 강제는 코어가 맡는다.
- 다중 프로세스 쓰기는 `retrieval-serving.md` 2.7절이 잰 stdio 서버 8개 800건 무오류와 같은 구조다.

### 3.3 사람이 쓰는 파일 입력

Markdown + YAML 프런트매터 폴더를 적재했다. 식별자는 경로가 아니라 프런트매터의 `id`다 [M16].

| 단계 | 시간 | 결과 |
|---|---:|---|
| 첫 적재 2,000개 | 7,217 ms | ID 부여 후 원자적으로 파일에 기록. `FULL`, `L=1.3` |
| 무변경 재실행 | 69 ms | 2,000개 전부 stat으로 건너뜀 |
| `touch`만 | 80 ms | 해시 동일, 새 버전 없음 |
| 1개 수정 | 93 ms | 새 버전 |
| 이름 변경 | 68 ms | 같은 레코드 유지 |
| 삭제 | 68 ms | 행 삭제 없이 `status=dead` |
| 세션이 먼저 고친 파일을 사람이 수정 | 73 ms | 덮어쓰지 않고 충돌 기록, DB는 세션 내용 유지 |

충돌 판정은 파일 색인이 기억하는 `base_version`과 DB 버전의 비교다. 충돌 해소 UI는 범위 밖이고 지금은 기록만 남긴다.

**상시 감시 프로세스 없이 감지할 수 있다.** systemd `.path` 유닛은 사용자 매니저 안의 inotify로 동작한다. 실제 유닛으로 쟀다 [M16].

- 파일 쓰기에서 행이 보이기까지 66~87 ms다.
- **재귀하지 않는다.** 감시 목록에 없는 하위 폴더의 쓰기는 감지되지 않았다. 문서는 재귀 여부를 적지 않는다 [S16].
- **서비스 실행 중의 변경은 놓친다.** 연속 쓰기에서 격번으로 감지가 빠졌고, 다음 이벤트 때 함께 처리됐다(`created: 2`). 주기 타이머로 스윕을 더해야 한다. 적재가 멱등이라 겹쳐도 안전하다.
- inotify는 다른 머신이 NFS에서 바꾼 파일을 못 본다 [S16]. Windows 쪽에서 `\\wsl$`로 편집할 때의 동작은 재지 않았다.

### 3.4 수집 적재와의 공존

한 트랜잭션이 쓰기 락을 쥐는 시간이 대화형 쓰기의 지연이다 [M2].

| 긴 트랜잭션 | 잠금 시간 | 대화형 쓰기 p95 / 최대 | 읽기 p95(상세/이웃/검색) | 오류 |
|---|---:|---:|---:|---:|
| 2만 행 | 635~718 ms | 630 / 733 ms | 0.27 / 6.4 / 3.2 ms | 0 |
| 20만 행 | 6,429~7,117 ms | 7,037 / 7,143 ms | 0.30 / 8.4 / 3.5 ms | 0 |

읽기는 영향을 받지 않고 쓰기만 줄을 선다. dlt 적재를 한 트랜잭션으로 넣으면 그동안 MCP 쓰기가 수 초 대기한다. 선형 외삽하면 대화형 p99를 100 ms 안에 두려면 트랜잭션당 약 2,500행 이하가 된다(추정, 미측정). `busy_timeout`은 가장 긴 적재보다 길게 잡아야 한다. 측정 중 5초 설정에서는 16 작성자 무제한 쓰기로 `database is locked`가 1건 났고, 30초에서는 없었다.

### 3.5 지켜야 할 SQLite 규칙

**`BEGIN IMMEDIATE`만 쓴다.** 읽고 나서 쓰기로 승격하는 경로는 재시도로 막히지 않는다.

- 프로브: 다른 연결이 커밋한 뒤 승격을 시도하자 `busy_timeout` 5초와 무관하게 0.01 ms 만에 `SQLITE_BUSY_SNAPSHOT`으로 실패했다 [M2].
- 부하: DEFERRED 8 작성자, 12초에 잠금 오류 2,243,636건, 성공 약 1,700쌍이다 [M2].
- 문서도 승격이 불가하면 쓰기가 `SQLITE_BUSY`로 실패한다고 적는다 [S2]. busy 핸들러 언급은 없고, 위 프로브가 그 빈칸을 메운다.

**WAL 체크포인트를 방치하지 않는다.** 문서는 체크포인트 기아 시 "the WAL file will grow without bound"라고 적는다 [S1]. 읽기가 끊이지 않으면 실제로 그렇다 [M2].

| 초당 519쌍 + 읽기 프로세스 8개 | WAL 최대 | 체크포인트 | 쓰기 최대 |
|---|---:|---:|---:|
| 기본 자동 체크포인트 | 678.7 MB(안전장치 근접) | 해당 없음 | 24 ms |
| 2초마다 `TRUNCATE` | 321 MB | p50 38 ms, 최대 2,010 ms, 1회 busy | 2,041 ms |
| 2초마다 `RESTART` | 111.6 MB | p50 18.8 ms, 최대 19.2 ms | 21 ms |

유지 프로세스는 `RESTART`가 낫다. 실제 부하(초당 수십 쌍)에서 WAL은 4~25 MB였다 [M2]. 적재 직후 타이머에서 한 번 돌리면 충분해 보인다.

**연결을 스레드 간에 공유하지 않고, 예외에서 트랜잭션을 반드시 닫는다.** 계약 시험이 프로토타입의 버그를 잡았다. 잘못된 파라미터가 스레드 로컬 연결을 열린 트랜잭션 상태로 남기자 그 스레드의 이후 요청이 전부 `cannot start a transaction within a transaction`으로 500이 됐다 [M18]. 부하 시험에는 잘못된 입력이 없어 드러나지 않았다.

**동기화는 데이터별로 나눌 수 있다.** 설정이 연결 단위라서 사용자 쓰기는 `FULL`, 수집은 `NORMAL`로 둘 수 있다. 8세션 2쌍/s에서 쓰기 p50은 `FULL` 3.40 ms, `NORMAL` 0.43 ms다 [M2]. `NORMAL`은 전원 손실 시 최근 커밋이 되돌려질 수 있다(`graph-store.md` S49).

## 4. 다중 쓰기 실측과 저장 계층 순위

### 4.1 두 번째 쓰기 프로세스

두 프로세스가 같은 저장소를 읽기-쓰기로 열고 3초간 쓴 결과다 [M3].

| 엔진 | 두 번째 프로세스 | 확인 응답 / 최종 행 |
|---|---|---|
| SQLite WAL | 정상 | 293,241 / 293,241 |
| LadybugDB 0.22.1 | 거부 `Could not set lock on file` | 1,314 / 1,314 |
| LadybugDB `enable_multi_writes=True` | 같은 거부 | 1,303 / 1,303 |
| Grafeo 0.6.0 | 거부 `database file cannot be locked for reading` | 163,128 / 163,128 |
| DuckDB 2.0.0 | 거부 `Could not set lock on file` | 4,452 / 4,452 |
| Turso 0.8.3 기본 | 거부 `File is locked by another process` | 188,916 / 188,916 |
| Turso `multiprocess_wal` | 둘 다 쓰지만 `database is locked` 다수 | 139,448 / **140,762** |

`graph-store.md` 미해결의 `enable_multi_writes`는 이로써 정리됐다. 프로세스 간 쓰기에는 도움이 안 된다. 잠금 거부는 데이터를 지켰고, 모든 거부 엔진에서 유실은 없었다.

**Turso 실험 플래그의 숫자가 맞지 않는 이유를 ID별로 추적했다** [M3].

| 라운드 | 성공 응답 | 실패 응답 | 최종 행 | 실패 응답인데 커밋됨 |
|---|---:|---:|---:|---:|
| 1 | 119,668 | 4,511 | 120,738 | 1,070 (23.7%) |
| 2 | 111,258 | 4,437 | 112,277 | 1,019 (23.0%) |
| 3 | 109,607 | 4,473 | 110,669 | 1,062 (23.7%) |

성공 응답 유실은 0건이고 무결성 검사도 통과했다. 그러나 실패로 보고한 쓰기의 약 4분의 1이 커밋됐다. 멱등 키 없이 재시도하면 중복이 된다. 공식 문서도 다중 프로세스를 "No multi-process access", 플래그는 "not production ready"라고 적고 MVCC도 같다 [S9]. Turso FTS는 FTS5가 아니라 Tantivy 기반이고 `snippet()`이 없다 [S10]. 문서 안에서 "No ... triggers"와 `CREATE TRIGGER` 지원 표기가 충돌한다 [S9][S10]. 시험하지 않았다.

### 4.2 SQLite 다중 쓰기의 한계

읽기 프로세스 2개를 함께 돌렸다. 쓰기가 몇 개든 읽기 오류는 0건이었다 [M1][M2].

**무제한 쓰기, `FULL`, `L=1.3`, busy 5초** [M1].

| 작성자 | 쌍/s | 쓰기 p50 | p95 | p99 | 최대 | 읽기 p95 상세/이웃/검색 |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 199 | 6.0 | 6.3 | 7.5 | 15.7 | 0.43 / 4.1 / 3.6 |
| 2 | 216 | 7.1 | 17.7 | 60.9 | 235 | 0.45 / 4.2 / 3.9 |
| 4 | 233 | 6.9 | 58.3 | 234 | 1,536 | 0.53 / 4.9 / 5.0 |
| 8 | 244 | 8.4 | 136 | 538 | 1,936 | 0.54 / 5.2 / 5.0 |
| 16 | 258 | 13.0 | 264 | 839 | 2,218 | 0.52 / 5.2 / 4.8 |

처리량은 작성자 수와 무관하게 약 250쌍/s에서 멈춘다. "there can only be one writer at a time"이 그대로 드러난다 [S1]. 늘어나는 것은 공정성 없는 대기로 생기는 꼬리 지연이다. 작성자가 없는 쪽의 읽기는 영향이 없다.

**현실적 부하, 포아송 도착, busy 30초** [M2]. 쓰기 오류는 전부 0건이다.

| 부하 | 쌍/s | 쓰기 p50 | p95 | p99 | 최대 | WAL 최대 |
|---|---:|---:|---:|---:|---:|---:|
| 1세션 2쌍/s | 1.9 | 3.3 | 7.9 | 15.2 | 15.2 | 4.3 MB |
| 8세션 2쌍/s | 16.7 | 3.4 | 8.4 | 14.6 | 16.2 | 11.4 MB |
| 8세션 10쌍/s | 77.1 | 6.1 | 14.5 | 25.9 | 59.9 | 24.5 MB |
| 16세션 10쌍/s | 161.9 | 7.0 | 43.1 | 109 | 541 | 100.9 MB |
| 8세션 10쌍/s, `L=5` | 75.5 | 27.4 | 252 | 854 | 1,760 | 121.8 MB |
| 8 작성자 무제한, `L=20`, busy 5초 | 24.2 | 83.5 | 1,650 | 4,464 | 5,091 | 26.5 MB |

마지막 행만 조건이 다르고(M1) 잠금 오류가 2건 났다. 디스크가 20 ms급으로 느려지면 SQLite 쓰기 경합은 급격히 나빠진다. 현재 디스크의 1.2 ms는 여유가 크다.

### 4.3 서버형 후보

**임베디드 PostgreSQL 17.9**(`pgembed` 0.2.0, sudo 없이 pip 휠). 같은 작업 조합이다. 읽기 쿼리는 SQL로 옮겼고 이웃 질의가 단순해 SQLite와 직접 비교하면 안 된다 [M4].

| 8 | 244, 538 ms | 938, 10.6 ms | 74.9 ms |
| 16 | 258, 839 ms | 1,703, 12.1 ms | 99.5 ms |

| 현실적 부하 | SQLite p95 / p99 | PostgreSQL p95 / p99 |
|---|---:|---:|
| 8세션 2쌍/s | 8.4 / 14.6 ms | 10.3 / 15.6 ms |
| 8세션 10쌍/s | 14.5 / 25.9 ms | 12.5 / 18.7 ms |
| 16세션 10쌍/s | 43.1 / 109 ms | 11.9 / 19.2 ms |

운영 수치는 initdb 0.28초, 콜드 스타트에서 첫 질의까지 202~221 ms, 유휴 PSS 15.6 MB(프로세스 6개)다. `shared_buffers=128MB`가 아직 채워지지 않은 값이다. 예상보다 훨씬 가볍다. 쓰기 작업 중 읽기 p95는 상세 1.3~1.9 ms, 검색 13~43 ms로 검색이 SQLite(3.6~6 ms)보다 느렸다.

**시퀀스 커서 피드는 행을 놓친다.** 트랜잭션 A가 낮은 번호를 받고 열려 있는 동안 B가 높은 번호로 커밋하면, 폴러가 B를 보고 커서를 올린 뒤 A는 영영 보이지 않았다(`row_A_missed: true`) [M4]. 문서는 동시 트랜잭션을 막지 않으려고 시퀀스 값을 회수하지 않으며 틈이 생길 수 있다고 적는다 [S11]. 커밋 순서를 보장한다는 문구는 찾지 못했고, 어긋남은 위 재현으로 확인했다. PostgreSQL에서 커서 피드를 만들려면 스냅샷 경계나 논리 복제가 필요하다. SQLite는 작성자가 한 번에 하나라 `AUTOINCREMENT` 순서가 곧 커밋 순서다. 단일 작성자의 제약이 여기서는 이점이 된다.

**FalkorDB와 DuckDB Quack**(N 클라이언트, 1 트랜잭션 기준. SQLite의 쌍과 단위가 다르다) [M5].

| 구성 | 1 | 4 | 16 | 16세션 10건/s p95 | 쓰기 오류 |
|---|---:|---:|---:|---:|---:|
| FalkorDB AOF `always`, `L=1.3` | 220 tx/s | 508 | 482 | 6.5 ms | 0 |
| FalkorDB AOF `everysec`, `L=1.3` | 863 | 1,313 | 978 | 3.5 ms | 0 |
| DuckDB Quack, fsync 주입 없음 | 35 | 94 | 249 | 78.0 ms | 0 |

FalkorDB는 빠르고 안정적이었지만 다중 쿼리 트랜잭션이 없다(`graph-store.md` S14). 레코드, 버전, 멱등 키를 한 커밋에 묶는 쓰기 코어를 그대로 옮길 수 없다.

임베디드 PostgreSQL로 옮길 조건은 다음 신호로 판단할 수 있다(이번 측정에서 나온 임계값).

- 동시 쓰기 세션이 16개 가까이 지속되고 쓰기 p99가 100 ms를 넘는다.
- 초당 커밋이 지속적으로 수백 건에 이른다.
- 대화형 쓰기가 적재 트랜잭션 분할로도 지연을 벗어나지 못한다.

`pgembed`는 ★53, 최근 릴리스 2026-03-18이다. 주 저장소 공급망으로 쓰려면 버전 고정이나 다른 배포본(`pixeltable-pgserver` 0.7.1은 PostgreSQL 16.14)도 함께 봐야 한다. PGlite는 "only has a single exclusive connection"이라 다중 쓰기 해법이 되지 못한다 [S12].

SQLite 본가의 `BEGIN CONCURRENT`는 낙관적 페이지 잠금이지만 커밋은 여전히 직렬이다 [S7]. 표준 빌드에서 쓸 수 있는지는 문서에서 확인하지 못했다.

### 5.2 쓰기 작업 중 HTTP 읽기 지연

서버는 Starlette + uvicorn(스레드풀, 요청당 읽기 트랜잭션 1개), 부하는 별도 프로세스 2개의 닫힌 루프다. 단위는 ms이고 `p50 / p95 / p99`다 [M6].

| 시나리오(10k) | 상세 | 이웃(깊이 2, 200) | 검색 | 패싯 p95 | 개요 |
|---|---:|---:|---:|---:|---:|
| S0 쓰기 없음 | 1.1 / 2.0 / 2.4 | 3.1 / 9.2 / 14.8 | 3.0 / 5.3 / 6.3 | 52.6 | 71~93 |
| S1 8세션 2쌍/s, `FULL` | 1.1 / 2.0 / 2.6 | 3.1 / 8.7 / 15.0 | 3.2 / 5.7 / 7.1 | 51.4 | 71~79 |
| S2 2만 행 적재 반복 + 4세션 | 1.2 / 2.5 / 3.4 | 5.6 / 14.7 / 21.7 | 3.3 / 5.7 / 6.7 | 211 | 302~387 |
| S3 초당 500쌍 + RESTART | 1.3 / 2.2 / 2.7 | 3.4 / 8.2 / 15.4 | 3.3 / 6.2 / 7.2 | 49.9 | 65~90 |
| S4 S1 + `VACUUM INTO` 게시 | 1.0 / 1.7 / 2.3 | 2.7 / 7.3 / 12.8 | 2.6 / 4.4 / 5.3 | 41.6 | 54~63 |

오류는 전 시나리오 0건이다. 개요는 `max_sensitivity` 기본값에서 8,878 노드·36,012 엣지 2.19 MB를 돌려줬고, S2는 적재로 엣지가 193,727개로 늘어 9.67 MB가 됐다. `VACUUM INTO`는 쓰기 중 50~63 ms에 19 MB를 만들었다. 쓰기 쪽 p95는 S1 6.6 ms, S3 3.6 ms로 읽기 부하의 영향이 없었다.

규모별 결과다 [M7].

| 규모 / 시나리오 | 상세 p95 | 이웃 p95 | 검색 p95 | 패싯 p95 | 개요 |
|---|---:|---:|---:|---:|---:|
| 50k S0 | 1.6 | 11.3 | 17.9 | 331 | 546~574 ms, 44,349·178,897, 10.9 MB |
| 50k S1 | 3.5 | 15.6 | 22.5 | 331 | 512~579 ms |
| 50k S2 | 3.1 | 15.4 | 22.3 | 425 | 651~690 ms, 엣지 336,612, 18.4 MB |
| 200k S0 | 1.4 | 24.2 | 67.9 | 1,364 | 1.68~1.74 s, 10만·466,710, 27.8 MB |
| 200k S2 | 6.7 | 36.2 | 85.1 | 1,826 | 1.99~2.11 s, 10만·50만, 29.3 MB |

목표(상세·이웃·검색 p95 200 ms, 개요 2초)는 20배 규모까지 통과했다. 개요만 200k S2에서 경계에 닿는다. 다만 1만 노드 목표를 10만 노드로 키운 값이다.

**병목은 패싯이다.** 내 구현의 `source_host` 집계가 엣지를 훑기 때문이다. 노드 컬럼 패싯만이면 10k 3.4 ms, 50k 21.4 ms이고 전체는 29.4 ms, 184.8 ms다. 검색 필터 패싯은 9.5 ms, 75 ms다 [M20]. 출처 호스트를 색인된 컬럼으로 두면 대부분 해결될 것으로 보인다(미측정).

**as-of 조회.** `as_of_valid`, `as_of_observed`는 상세 p95 0.1 ms, 이웃(깊이 2) p95 1.6~5.1 ms다 [M20]. 일부 ID가 해당 시점에 없어 일찍 끝나므로 낙관적인 값이다. 프로토타입은 **검색과 개요 노드에 as-of를 구현하지 않았다.** 현재 FTS는 최신 본문만 색인한다. 계약은 "모든 읽기의 공통 파라미터"이므로 버전별 색인 또는 후처리 필터를 정해야 한다. 재지 않았다.

### 5.3 읽기 전용 파일 접근의 함정 (소비자 요구 6)

`sagae-tools`의 재현을 전부 확인했고 사실을 둘 더했다 [M11].

| 경우 | 결과 |
|---|---|
| 깨끗한 WAL DB, 쓰기 가능 폴더, `mode=ro` | 성공. `-shm`, `-wal` 생성 **확인** |
| 깨끗한 WAL DB, 읽기 전용 폴더, `mode=ro` | **실패** `attempt to write a readonly database` 확인 |
| 깨끗한 WAL DB, 읽기 전용 폴더, `immutable=1` | 성공, 파일 생성 없음 |
| `journal_mode=DELETE` 사본, 읽기 전용 폴더, `mode=ro` | 성공 |
| 쓰기 프로세스 가동 중, `mode=ro` | 성공, 최신 2행 |
| 쓰기 프로세스 가동 중, `immutable=1` | **오류 없이 낡은 값 1행** |
| `VACUUM INTO` 산출물 | `journal_mode=delete` |
| DuckDB 2.0.0 읽기 전용 연결이 열린 동안 쓰기 연결 | **거부** `Could not set lock on file` 확인 |

문서도 읽기 전용 WAL 조건을 같이 적는다 [S1]. 파일 경로를 대체 수단으로 둔다면 답은 게시 사본이다. `VACUUM INTO` 결과는 그 자체로 읽기 전용 폴더에서 열린다. `immutable=1`을 라이브 DB에 쓰면 안 된다.

### 5.4 스냅샷 원자 게시 (재빌드·게시 중 읽기 동작)

`VACUUM INTO` → `build_id` 기록 → `chmod 444` → `os.replace`를 0.5초 간격으로 14회 반복하고, 읽기 프로세스 3개가 매번 새로 열어 읽었다. 쓰기 프로세스도 함께 돌렸다 [M19].

|---|---:|---:|
| 게시 p50 / 최대 | 37.2 / 42.5 ms | 40.9 / 59.2 ms |
| 읽기 횟수(3개 합) | 124,752 | 120,623 |
| 오류 | 0 | 0 |
| `build_id` 역행 | 0 | 0 |
| 열고 질의 p50 / p99 | 0.18 / 0.35 ms | 0.18 / 0.39 ms |

### 5.5 스냅샷 형식 (소비자 요구 4)

1만 노드·5만 엣지 전체다 [M17].

| 형식 | 인코딩 | 크기 | gzip-6 | zstd-3 | 비고 |
|---|---:|---:|---:|---:|---|
| 객체 배열 JSON | 8.7 ms | 5.18 MB | 0.61 MB | 0.68 MB | 사람이 읽기 쉬움 |
| **컬럼 배열 JSON** | 21.3 ms | 3.16 MB | 0.55 MB | 0.59 MB | `columns` + 값 배열 |
| NDJSON | 193 ms | 6.02 MB | 0.62 MB | 0.69 MB | 스트리밍 가능 |
| Graphology 직렬화 | 58 ms | 5.59 MB | 0.63 MB | 0.65 MB | `import()` 직행 |
| Cytoscape | 40 ms | 5.17 MB | 0.60 MB | 0.66 MB | |
| G6 | 33 ms | 5.17 MB | 0.62 MB | 0.65 MB | |
| Parquet(zstd) 노드+엣지 | 80 ms | 0.45 MB | | | 분석 친화, TS 파서 필요 |
| SQLite `VACUUM INTO` | 38 ms | 18.9 MB | | | 본문과 이력 포함 |

Bun의 `JSON.parse`는 18~27 ms, zstd 해제 포함 22 ms다. 형식 차이는 압축 후 거의 사라진다. 로컬 루프백이면 압축도 필요 없다. 그래서 라이브러리별 형식을 KB가 내는 대신 컬럼 배열 하나만 정하고 어댑터를 뷰어에 두는 편이 단순하다. OpenAPI 3.2 목차에는 순차·스트리밍 미디어 타입 절이 있다 [S26]. NDJSON 스트리밍을 계약에 넣는다면 3.2가 유리할 수 있으나 세부는 확인하지 못했다.

### 5.6 변경 피드 (소비자 요구: 커서 기반)

`change_log` 표와 트리거(아웃박스)로 구현했다 [M14].

| 방식 | 쓰기 p50 | 쓰기 평균 | 비고 |
|---|---:|---:|---|
| 피드 없음 | 68.2 µs | 96.5 µs | |
| 트리거 + `change_log` | 75.5 µs | 103.8 µs | 표 전체에 단일 순서. 약 7 µs 증가 |
| `sqlite-chronicle` 0.6.1 | 75.3 µs | 100.5 µs | 표마다 그림자 표, 최신 행 상태만 |

- 100만 행 로그에서 500행 폴링 p50 0.24 ms, 최대 seq 조회 3.1 µs, `PRAGMA data_version` 2.8 µs다.
- 90만 행 압축 삭제는 116.5 ms다.
- 커서가 압축선 아래로 내려가면 410을 돌려주게 했고, 시험에서 `cursor expired`, `oldest available seq is 16`을 확인했다 [M20]. 소비자는 스냅샷으로 재동기화한다.

`sqlite-chronicle`은 표별 `__version`이고 현재 행만 돌려준다. 중간 변경을 잃으므로 변경 내역 화면에 맞지 않고, 표를 가로지른 순서도 없다. 트리거는 수 줄이고 dlt 같은 외부 작성자의 쓰기도 잡는다. 지침 2(재발명 금지)를 따져도 이쪽이 더 얇다.

| 오류 | RFC 9457 `application/problem+json` | [S19], 구현 |

| 페이지네이션 | 키셋 커서. `(정렬 키, rid)`를 base64url로 감싼 불투명 토큰, 정렬 키는 허용 목록 | 동시 삽입 중 401행, 중복 0, 누락 0 [M20] |
| 시점 지정 | 쿼리 파라미터 `as_of_valid`, `as_of_observed` | 소비자 요구. Memento의 `Accept-Datetime` [S20]은 한 시간축만 다뤄 두 축에 맞지 않음 |
| 조건부 GET | `ETag: "seq-N"`, `If-None-Match`로 304 | 구현 확인 [M6]. DB 전역 값이라 어떤 변경이든 전체 무효화된다. 30~60초 폴링에는 충분 |

타입 관련 값은 닫힌 `enum`으로 쓰면 안 된다. oasdiff가 응답 enum 값 추가를 경고한다(`response-property-enum-value-added`) [M18]. 타입이 런타임에 늘어나는 범용 DB에서는 `type`을 문자열로 두고 `/v1/schema`로 구동하는 것이 소비자 요구("타입을 하드코딩하지 않고 UI를 구동한다")와도 맞다. `origin`, `sensitivity`처럼 고정된 값만 enum으로 둔다.

Schemathesis 수정 후에 남은 3건은 계약과 구현의 불일치다. `limit=5001`을 거부하지 않고 잘라 쓴 것, `/v1/changes`의 400이 문서에 없는 것, 토큰이 없는 `q`를 400으로 거부한 것이다 [M18]. 경계값 처리 규칙을 계약에서 정해야 한다.

## 6. HTTP와 상시 프로세스 최소화의 양립

### 6.1 구성 선택지

| 안 | 구조 | 첫 호출 | 웜 호출 | 유휴 | 판단 재료 |
|---|---|---:|---:|---:|---|
| A. 소켓 활성화 | systemd가 소켓을 쥐고 첫 연결에 기동, 유휴 시 종료 | 150 ms | 2.3 ms | 0 | KB가 계약 전체를 소유. 로컬 재부팅 후에도 동일 |
| B. 게이트웨이 + CLI | 게이트웨이가 호출마다 `kb` 실행 | 22~36 ms | 동일 | 0 | 가장 단순. 게이트웨이 오버헤드 미측정 |
| C. 게이트웨이 내장 TS 코어 | 게이트웨이가 `bun:sqlite`로 직접 읽음 | 프로세스 내 | 웜 수 ms | 0 | 빠르지만 읽기 구현이 Python, TS로 이중화 |
| D. 상시 데몬 | 항상 떠 있음 | 없음 | 2.3 ms | PSS 39 MB | R13 위배. A 대비 이득은 첫 요청 150 ms뿐 |

A와 B는 같은 코어를 쓰므로 계약이 같으면 소비자는 어댑터만 바꾼다. **기본 A, 게이트웨이가 생기면 B 또는 A를 뒤에 두는 구성**이 근거에 맞다. C는 저장 구조가 굳은 뒤에 재검토할 수 있다. 소비자가 원치 않은 "저장 구조에 묶임"을 KB 소유 라이브러리로 옮길 뿐 없애지는 못한다.

### 6.2 소켓 활성화 실측 [M9]

실제 사용자 매니저는 건드리지 않았다. `etl-orchestration.md` 부록 B의 비공개 매니저(사용자 네임스페이스, scratchpad XDG 경로, 전용 하위 cgroup)에서 진짜 `.socket` 유닛을 돌렸다.

| 항목 | 값 |
|---|---:|
| 첫 응답(콜드) 12회 | p50 150.1 ms, 범위 130~169 ms |
| `systemd-socket-activate` 단발 8회 | p50 111.2 ms, 최대 120.8 ms |
| 웜 300회(연결마다 새로) | p50 2.3, p95 3.0, p99 3.4 ms |
| 서버 PSS / RSS | 39.0 / 45.3 MB |
| 유휴 종료 뒤 | 서비스 `inactive`, 소켓 `listening`, 메모리 0 |
| 종료 시점 전후 요청 60회 | 실패 0건, 최대 232 ms |
| Unix 소켓 콜드 / 웜 p50 | 123~174 ms / 1.7 ms, 권한 0600 |

소켓은 유닛이 계속 쥐고 있다. `FlushPending=` 설명대로 기본값에서는 서비스가 재시작해도 대기 연결이 지워지지 않는다 [S13]. `Accept=no`면 "only the first connection will have to pay the activation resource cost"다 [S13]. 전달 규약은 `LISTEN_PID`, `LISTEN_FDS`, fd 3이다 [S15]. uvicorn의 `fd=3`이 TCP와 Unix 소켓 모두에서 동작했다. 소스는 `socket.fromfd(fd, AF_UNIX, ...)`라고 쓰지만 TCP도 문제없었다.

**함정: 시작 제한.** 처음 유휴 종료 경합을 의심했으나 틀렸다.

- 기본값은 `DefaultStartLimitIntervalSec=10s`, `DefaultStartLimitBurst=5`다 [S17].
- 6번째 활성화가 `Result=start-limit-hit`로 거부되고, 소켓 유닛도 `failed (service-start-limit-hit)`가 되어 수신을 멈췄다.
- 이후 연결은 3초 타임아웃으로 실패했고, 40초 넘게 복구되지 않았다.
- 문서는 한도 뒤 "from a timer or socket at a later point, after the interval has passed" 재시작할 수 있다고 적는다 [S18]. 소켓 유닛 자체가 멈추는 경우에는 그렇게 동작하지 않았다.
- `StartLimitIntervalSec=0`으로 해결했다. 이 값은 "disable any kind of rate limiting"이다 [S18].

유휴 시간을 폴링 주기보다 길게 잡으면 정상 운영에서는 잘 닿지 않는다. 그러나 코어 크래시 반복이면 닿는다. 그때 API 전체가 죽으므로 제한을 끄거나 크게 잡는 쪽이 낫다. 크래시 감지는 별도로 필요하다.

검증한 유닛 형태다. 실제 설치는 사용자 승인 뒤의 일이다.

```ini
# kb-read.socket
[Socket]
ListenStream=%t/kb-read.sock     # 또는 127.0.0.1:<포트>
SocketMode=0600
Accept=no

# kb-read.service
[Unit]
Requires=kb-read.socket
StartLimitIntervalSec=0
[Service]
Type=simple
Environment=KB_DB=<경로> KB_IDLE_EXIT=<초>
ExecStart=<python> -I kb_http.py
```

유휴 종료는 uvicorn이 SIGTERM을 받아 시그널로 끝나는 형태라 `ExecMainStatus=15`가 남지만 `Result=success`다.

WSL 조건도 따라온다.

- 사용자 유닛은 사용자 매니저가 떠 있어야 동작한다. 현재 `Linger=no`이고 로그인 세션이 있어 떠 있다(`etl-orchestration.md` 5.3절).
- 유휴 판정에 systemd 서비스는 들어가지 않으므로 소켓 유닛이 distro를 살려 두지 않는다(같은 문서 5.2절). 뷰어가 같은 WSL에서 돈다면 문제되지 않는다.
- systemd 없는 곳으로 옮기면 D로 돌아가면 된다. 코어는 같다. `Bun.serve`의 fd 수신은 재지 않았다.
- 프로토콜 프록시가 필요하면 `systemd-socket-proxyd --exit-idle-time=`이 있다 [S14]. 소켓 활성화를 모르는 서버 앞에 둘 수 있고, 이번에는 재지 않았다.

### 6.3 조회 코어 공유

| 표면 | 코어 호출 | 콜드 | 호출 지연 | PSS |
|---|---|---:|---:|---:|
| HTTP(uvicorn + Starlette) | 같음 | 111~150 ms | p50 1~3 ms | 38~39 MB |
| HTTP + MCP 한 프로세스 | 같음 | 537 ms(최대 576) | 미측정 | 88.6 MB |
| MCP stdio(FastMCP) | 같음 | 0.739 s | `kb_get` p50 3.54, p95 7.05 ms | 미측정 |
| CLI(표준 라이브러리) | 같음 | 호출마다 | 상세 p95 25.3, 이웃 39.4, 검색 26.9 ms | 호출 중만 |

같은 스냅샷에서 MCP의 `structured_content.data`와 HTTP의 `data`가 일치했다(`True`, `build_id` 동일) [M10].

임포트 비용이 구조를 정한다 [M8].

| 임포트 | p50 | p95 |
|---|---:|---:|
| Python 기동 | 11.6 ms | 13.3 ms |
| `sqlite3` | 13.8 ms | 19.0 ms |
| `orjson`, `uvicorn`, `starlette` | 111 ms | 152 ms |
| `fastmcp` | 250 ms | 462 ms |
| Kiwi 적재(`retrieval-serving.md`, RSS 523 MB) | 590~770 ms | 미측정 |

**코어는 표준 라이브러리만 의존해야 한다.** 그래야 CLI가 25 ms대로 유지된다. 한국어 검색을 문자 bigram으로 두면 읽기 경로에 Kiwi가 필요 없다. bigram이 Kiwi와 품질 차이가 없다는 것은 `retrieval-serving.md` 5.1절에서 쟀고, 이번 무콘텐츠 FTS도 2음절 포함 8개 질의 재현율 1.000이다 [M20]. 벡터 검색은 MCP 쪽에만 두면 HTTP 콜드 스타트를 지킨다.

스니펫과 하이라이트는 FTS5 `snippet()`이 아니라 앱에서 계산했다. 질의 항을 표시 본문에서 다시 찾으므로 토큰화와 무관하고 언어 중립이다. 덕분에 `graph-store.md`의 APSW 토크나이저 의존(`no such tokenizer`)이 사라지고, 표준 `sqlite3`와 `bun:sqlite` 모두 같은 DB를 읽는다. Bun 판도 같은 질의로 동작했다 [M6].

### 6.4 Python과 Bun 비교

| 항목 | Python 스레드풀 | Bun 단일 루프 |
|---|---:|---:|
| 10k 개요 | 71~93 ms | 36~43 ms |
| 10k 상세 p50 / p95 | 1.1 / 2.0 ms | 0.6 / 2.7 ms |
| 200k 상세 p50 / p95 | 1.1 / 1.4 ms | 0.9 / 54.4 ms |
| 200k 검색 p95 | 67.9 ms | 91.9 ms |
| 10k S0 처리량 | 447 rps(패싯 포함) | 1,163 rps(패싯은 미구현) |

`bun:sqlite`는 동기 API다 [S32]. 요청 하나가 도는 동안 이벤트 루프가 막혀 짧은 조회가 무거운 검색 뒤에 줄을 선다. p50은 빠른데 p95가 나빠지는 까닭이다. Python은 `sqlite3`가 질의 중 GIL을 놓아 스레드가 앞지른다. 20만 규모에서 이 차이가 커진다. 소비자가 한 명이고 동시 요청이 적어 목표 안이지만, 게이트웨이 내장(안 C)에서는 고려할 점이다. Bun이 Python이 쓰는 WAL DB를 FTS5까지 정상으로 읽는 것은 확인했다 [M6].

이 사실에서 나오는 인터페이스 조건이다.

1. **엣지에 항상 `id`를 준다.** G6의 기본값 `${source}-${target}`은 평행 엣지에서 충돌한다.
2. **개요는 양끝이 모두 포함된 엣지만 낸다.** 프로토타입이 그렇게 한다. 트렁케이션이 나도 끊어진 엣지가 나오면 안 된다.
3. **좌표를 내지 않는다.** 레이아웃은 도구 계산으로 합의돼 있다. Sigma는 `x`, `y`가 없으면 배치할 수 없으므로 뷰어가 채운다.
4. **`rid` 순서를 안정적으로 유지한다.** cosmos.gl의 인덱스 입력은 노드 배열 위치로 만들 수 있다. 공개 계약에는 `rid`를 넣지 않고 순서만 보장한다.
5. **ID는 문자열이다.** 전 라이브러리가 받는다.
6. **라벨, 타입만 개요에 넣는다.** 본문은 상세에서 가져온다. 2.19 MB의 대부분이 ID와 라벨이다.

### 8.2 장애 영역 [M24]

읽기 전용 조회 결과다.

- 물리 디스크는 `SHPP41-2000GM` SSD 1개(2 TB)이고 볼륨은 C:(NTFS, 1,862 GB) 하나다.
- `ext4.vhdx`는 `C:\Users\user\AppData\Local\Packages\CanonicalGroupLimited.Ubuntu_79rhkp1fndgsc\LocalState`에 있다.

따라서 `/mnt/c` 사본은 ext4나 vhdx 손상을 막지만 SSD 고장, 랜섬웨어, 분실은 막지 못한다. 머신 밖 대상만 막는다.

Microsoft 문서는 갑작스런 종료나 정전이 "mounting the distribution disk" 오류와 읽기 전용 전환을 부를 수 있고, 그 상태의 `remount,rw` 변경은 재시작 시 사라진다고 적는다 [S46]. 복구는 `wsl --mount --vhd --bare` 후 `e2fsck`다 [S46]. `AppData` 안 파일을 Windows 도구로 건드리지 말라는 경고도 있다 [S46]. `wsl --export`는 tar 또는 `--vhd` 스냅샷을 만든다 [S47]. 배포판 전체 사본이라 복구 경로로는 쓸 수 있으나 같은 디스크에 두면 의미가 없다.

머신 밖 후보다.

|---|---|---|
| Proxmox 클러스터 | 3노드 온라인, 정족수 정상. `local-lvm` 57.9 / 151.6 / 151.6 GB, `local` 41.5 / 72.7 / 72.7 GB [M24] | 공유 스토리지 없음, PBS 목록에 없음. 집 안 같은 장소일 수 있음. 자격 증명 설정 필요 |

| GitHub 비공개 저장소 | 권장 1 GB 이하, 5 GB 미만 강력 권장, 100 MiB 초과 파일 차단 [S48] | 텍스트 내보내기 전용. `secret`은 넣지 않음 |

### 8.3 후보 실측

**restic 0.19.1** [M21]. 체크섬을 검증한 공식 바이너리로 로컬 저장소에 돌렸다. 약 95~100 MB DB에 세대마다 노트 1,000개를 더했다.

| 스냅샷 방식 | 1세대 증가 | 2세대 | 3세대 | 백업 시간 |
|---|---:|---:|---:|---:|
| `VACUUM INTO` | 31.1 MB | **24.7 MB** | **20.4 MB** | 0.91초 |
| 백업 API(`conn.backup`) | 33.1 MB | **5.7 MB** | **5.2 MB** | 0.81~0.92초 |

`VACUUM INTO`는 페이지를 재배치해 내용 기반 분할 중복 제거가 잘 안 된다. 문서는 크기가 작다는 이점을 적지만 [S3], restic 위에서는 백업 API가 4배 이상 낫다. 문서도 백업 API가 CPU를 덜 쓰고 증분 실행이 가능하다고 적는다 [S3]. 용도를 나눈다. **게시 스냅샷은 `VACUUM INTO`, 백업은 백업 API**다.

| 항목 | 결과 |
|---|---|
| `check --read-data` | 1.04초, rc 0 |
| 복원 | 0.83초, SHA256 일치, `integrity_check` ok, 노드 55,000 |
| 팩 1바이트 변조 후 `check --read-data` | rc 1, `repository contains errors`(2회 모두). 이 옵션이 있어야 팩 내용까지 검사한다 [S55] |
| 변조 후 복원 | 변조 팩을 쓰는 세대는 rc 1, 파일 1개 실패. 안 쓰는 세대는 rc 0 |

저장소 파일은 AES-256으로 암호화되고 Poly1305로 인증된다 [S54]. `secret`이 있어도 머신 밖에 둘 수 있는 근거다. 비밀번호 분실은 복구 불능이므로 별도 보관이 필요하다. `check --json`은 `num_errors`, `broken_packs`를 낸다 [S45]. 타이머의 건강 신호로 쓸 수 있다.

**Litestream 0.5.17** [M22]. 파일 복제본으로 돌렸다.

| 시험 | 결과 |
|---|---|
| 동시 기록자 8세션, 읽기 2개 | 쓰기 p95 5.0 ms, 오류 0, 읽기 영향 없음 |
| 자원 | PSS 34.8 MB, CPU 3.0%, 복제본 38.5 MB(19 MB DB) |
| 정상 복원 | 263 ms, seq 일치, 무결성 ok |
| 기록자와 Litestream 동시 `kill -9` 3회 | 미복제 20 / 52 / 24행(약 160행/s에서 0.13~0.33초분), 복원 240~248 ms, 무결성 ok |
| 다운타임 중 8,000행 + `TRUNCATE` 후 재기동 | 최종 seq 일치 |

문서상 기본 `sync-interval`은 1초 [S44], 체크포인트는 Litestream이 맡고 "long-running read transaction"을 유지한다 [S43]. 앱의 자동 체크포인트를 끄라고 권하고 `busy_timeout` 5초를 권한다 [S42]. 내 시험은 기본 자동 체크포인트(1000)로 돌렸고 공백을 메웠다. 다만 부하가 낮았으므로 권고를 뒤집는 근거는 아니다. 데이터베이스마다 복제 대상은 하나이고 [S43], SFTP 복제본이 있어 Proxmox로 보낼 수 있다 [S44].

Litestream의 비용은 **상주 프로세스**다. R13과 정면으로 충돌한다. 대신 임시 프로세스 여러 개가 쓰는 구조에서도 오류 없이 동작했다.

**git + 결정적 내보내기** [M23]. `first_party` 1,467건을 레코드당 Markdown 한 파일로 내보내고 20세대 편집을 쌓았다.

| 항목 | 값 |
|---|---:|
| 첫 커밋 / 이후 커밋 p50 | 126 ms / 48 ms |
| `gc --aggressive` 후 `.git` | 0.68 MB |
| 번들 / 복제 | 0.43 MB, 13 ms / 51 ms, `fsck` 0 |

사람이 읽을 수 있고 diff가 되며 머신 밖 푸시가 쉽다. DB 파일을 git에 넣는 것은 아니다. `secret`은 내보내기에서 뺀다.

### 8.4 조합

| 층 | 수단 | RPO | 상주 | 대상 |
|---|---|---:|---:|---|
| 1. 로컬 빠른 복구 | 타이머 + 백업 API + restic | 타이머 주기 | 0 | ext4 또는 `/mnt/c` |
| 2. 머신 밖 | restic copy 또는 직접 원격 | 타이머 주기 | 0 | Proxmox, R2 |

R13을 지키면서 사용자 쓰기 직후의 손실 창을 줄이려면 첫 3층의 타이머 주기를 짧게 하거나, 쓰기 후 지연 트리거를 쓸 수 있다. restic 1회가 1초 안쪽이다. 몇 분 RPO로 충분한지는 사용자가 정할 일이다. 복원 훈련을 타이머로 정기 실행하는 것을 권한다. 이번처럼 `check --read-data`와 복원 후 `integrity_check`를 함께 돌리면 1~2초다.

**인용 오프셋(요구 2).** "쇼츠😀 광고 수익"에서 '광고'의 시작은 Python 4, JS 5다. 코드포인트 길이 9, UTF-16 10이다 [M20]. 이모지 앞뒤로 어긋난다. W3C 모델도 "unicode code points"를 기준으로 하고 `start`는 포함, `end`는 미포함이다 [S23]. 프로토타입의 오프셋을 표시 본문에 잘라 '광고'가 나오는 것을 확인했다.

한글에는 정규화 문제가 하나 더 있다. 같은 문자열의 NFD는 코드포인트 17개(Python), UTF-16 18이고, NFC 질의어가 NFD 본문에서 찾아지지 않는다(`find` -1) [M20]. **표시 본문은 적재 시 NFC로 고정해야 한다.** macOS 파일명, 일부 웹 원문이 NFD로 들어올 수 있다. W3C 모델은 선택 전 정규화를 요구한다 [S23]. JS 소비자는 코드포인트 오프셋 `n`을 `[...s].slice(0, n).join("").length`로 UTF-16 오프셋으로 바꿀 수 있다. 이 문자열에서 5는 6이 된다 [M20].

### 9.3 sagae-tools가 기다리는 질문

1. **예상 규모.** 저장소 문서에 근거가 없어 답하지 못한다. 측정으로는 20만 노드·100만 엣지까지 목표를 통과했다. 규모 가정의 여유는 약 20배다.
2. **실행 위치와 HTTP 데몬.** 로컬 WSL 기준으로 소켓 활성화가 가능하고 유휴 프로세스는 0이다. 설치는 사용자 승인 대상이다. Proxmox로 옮기면 같은 계약을 TCP + Bearer로 제공한다.
3. **출처 스냅샷 본문 형식.** 원본은 WARC, 표시 본문은 추출 텍스트 또는 Markdown을 NFC로 고정하는 안이다. 오프셋은 표시 본문 기준이다. 추출기별 변화는 재지 않았다.
4. **구현 언어와 동시 읽기.** 수집과 코어는 Python 전제다(dlt, Kiwi, FastMCP). Bun 게이트웨이 프로세스 안에서는 호출할 수 없다. 대신 CLI, HTTP, 또는 KB가 관리하는 TS 읽기 라이브러리다. 동시 읽기는 같은 호스트의 다중 프로세스·스레드에서 안전하다. WAL은 네트워크 파일시스템에서 동작하지 않는다 [S1].

제안된 "KB는 라이브러리·CLI만, HTTP는 게이트웨이" 구성은 실측상 성립한다. 표준 라이브러리 CLI가 p95 25~42 ms다. 관제 서버가 아직 없으므로 게이트웨이 오버헤드는 미측정이다.

def bigrams(text):                       # 한글 연속은 겹치는 bigram, 라틴·숫자는 소문자 한 토큰

## 12. 미해결

- **실제 ext4에서의 DB 측정.** fsync 호출 지연만 모사했다. 저널 경합, `discard`, 콜드 페이지 캐시는 없다. 재부팅 직후 첫 읽기와 콜드 스타트는 더 느릴 수 있다.
- **전원 손실.** `kill -9`까지만 쟀다. vhdx 위 fsync가 물리 매체까지 닿는지, 1.2 ms가 실제 플러시인지도 확인하지 못했다.
- **머신 밖 복원.** Proxmox, R2, GitHub 어디로도 실제 백업·복원을 돌리지 않았다. 자격 증명이 없고 설정 변경은 사용자 승인 대상이다.
- **RPO 목표.** 몇 분까지 허용할지는 사용자 결정이다. Litestream 상주 여부가 여기에 달렸다.
- **as-of 검색과 개요 노드.** 계약은 모든 읽기를 요구하지만 프로토타입은 상세, 이웃, 관계만 구현했다.
- **민감도와 인증의 결합.** 토큰 범위 설계 미정. 현재 프로토타입은 쿼리 파라미터로 상승할 수 있다.
- **벡터 검색과의 공존.** 쓰기 코어에 임베딩을 넣지 않았다. MCP 쪽 비용은 `retrieval-serving.md`를 따른다.
- **블록 수준 링크.** 필요 여부 미정.
- **`.path`와 Windows 편집기.** `\\wsl$` 경유 편집의 inotify 동작을 재지 않았다.
- **게이트웨이 오버헤드.** `sagae-tools` 관제 서버가 없다. 안 B의 총 지연은 미측정이다.
- **`Bun.serve` 소켓 활성화.** fd 수신을 재지 않았다.
- **임베디드 PostgreSQL 장기 운영.** 업그레이드, 충돌 복구, `pg_dump` 백업을 재지 않았다. 패키지 지속성도 불확실하다.
- **Linger.** 부팅 경로에서 소켓 유닛이 뜨는지는 `etl-orchestration.md` 미확인 2번과 같은 문제다.
- **문서 확인 불가.** 표준 SQLite 빌드에서 `BEGIN CONCURRENT` 사용 가능 여부, Turso 트리거 지원, cosmos.gl 규모 수치, vis-network·reagraph 입력 형식은 확인하지 못했다.
- **실제 분포.** 민감도, 타입, 허브 분포는 가정이다. `first_party` 비율이 달라지면 패싯과 개요가 달라진다.
