## Spike 1

No maintained candidate is acceptable as shipped. agentgateway, 1MCP, mcp-use and fastmcp-ts all rewrite resource URIs but not resource_link, so a link in a tool result cannot be read back (reproduced through real Claude Code on agentgateway and 1MCP). The SDK v2 composition was the only one to pass every check: 207 lines (floor 38), no protocol translation, URIs unchanged, one stable stdio child, respawn, and immediate pickup of a new upstream in a running Claude Code session. Best product is agentgateway (43 MB, 125 ms, bearer, the only product relaying input_required), but on a merged route it spawned the stdio target on every modern request (25 of 25, about 100 ms), and a running session never saw a new upstream. 1MCP has the best product stdio recovery, but costs 319 MB, has no static bearer and a 60 s call limit. Claude Code negotiated 2026-07-28 and fell back to initialize only on agentgateway with a legacy-only target. Deferred loading worked and tool-level alwaysLoad survived. The composition needed 4 fixes found by this rig (177 to 207 lines), and about 60 more lines are estimated before production. The report file does not exist: the harness refused it, and I did not route around that, so the full findings are in these fields.

### Recommendation

Ranking: 1. SDK v2 composition inside the control server, Hono on Node 26. 2. agentgateway. 3. 1MCP. 4. mcp-use. 5. fastmcp-ts.

Answer to the question: no maintained candidate has acceptable fidelity as shipped, because all four break resource_link read-back and no product has a setting to avoid it. The least custom code with acceptable fidelity is the SDK composition. It respects the no-translation rule: none of its lines parse JSON-RPC or handle eras, Mcp-Name or session headers, because the SDK does that on both legs. What the project owns is routing and lifecycle. That ownership has a real cost: this rig found 4 defects in my first version (no recovery from a restarted session-based upstream, the 60 s SDK default cutting long calls, no input_required relay, one hung upstream stalling tools/list for 60 s), and fixing them took 30 lines. Keep the harness as its regression suite.

Custom code the winner requires. Already written, 207 lines: merge and routing 82, upstream lifecycle 68, imports and constants 22, config reload 22, shutdown 7, HTTP glue and bearer 6. Still to write, about 60 lines by estimate: capped exponential backoff with a stop (12), per-upstream call timeout, since the 30-minute default leaves calls to a hung upstream hanging (5), last-good list per upstream, since each tools/list costs 3 s while one hangs (15), constant-time token compare and token from EnvironmentFile (3), per-upstream instruction budget (5), health endpoint and request log, scope depends on what 관제 means (15 to 20), name validation and a duplicate-URI rule (5). Known limits to accept: a legacy upstream's elicitation is not relayed, there is no upstream OAuth, prompts/get and resources/templates/list are written but unexercised, and it shares a crash domain with anything else in that process.

If no custom gateway is read strictly: use agentgateway with HTTP targets only, plus failOpen and policies.timeout.backendRequestTimeout, and keep URIs out of tool results. External stdio servers would then need a long-lived stdio-to-HTTP adapter, which I did not test, and running sessions would not see new upstreams until restarted.

First check for any product route: whether the proxmox MCP answers server/discover. Its era decides which agentgateway and 1MCP stdio problem applies. The composition is indifferent. I did not touch it.

What would change the ranking: agentgateway wins if the design drops URIs from tool results and all upstreams are HTTP. 1MCP improves if its timeout setting works and it leaves SDK 1.30.0. Any product that passes resource_link correctly displaces the composition.

Not tested: Claude Code reconnecting after a mid-session gateway restart and recovery after session TTL expiry (VG-C5, #95018, #96733), permission patterns across merged names, a stdio server that ignores stdin EOF, agentgateway condition rules to narrow spawns, the stdio-to-HTTP adapter, 1MCP async mode with an upstream down at start, conformance 0.2.0-alpha.12, socket activation and idle exit, and the real proxmox MCP by instruction. Inspector CLI does not exercise the modern path.

### Verdicts

- **SDK v2 composition (client + createMcpHandler, 207 lines)**: pass. Only candidate to pass every check, including through real Claude Code on the final revision: URIs unchanged, resource_link readable, outputSchema, annotations, _meta and instructions kept, one stable stdio child for dual-era and legacy-only servers (0 spawns per call), respawn in about 1.13 s, session-based upstream recovery, immediate list_changed to a running session, bearer plus Host and Origin, 70 s calls, progress, cancel, input_required on a modern HTTP upstream. Not run through real Claude Code.

### Surprises

- Harness conflict: the task required report.md, but Write was refused with 'Subagents should return findings as text, not write report files'. I did not bypass it through Bash. No report file exists.
- All four maintained candidates fail resource_link read-back, each with a different URI scheme. VG-C10 predicted this for agentgateway only, and it also rewrites contents[].uri on read. prefixMode: conditional does not help.
- VG-C4 is worse than stated: on the modern path agentgateway spawns every stdio target on every request, even a tools/call bound for another target (25 of 25). The alpha reply does not wait for it, so alpha p50 stayed at 7.2 ms.
- VG-C6 is narrower than stated: only a legacy-only target drops the backend to legacy. A dual-era stdio target answers server/discover and the route stays modern, despite the README wording. failOpen does not help the legacy-only case.
- 1MCP's cross-era handling has a hidden cost: a legacy-only stdio upstream under a modern client spawns per call (20 of 20), while a dual-era one spawns 0.
- One HTTP upstream down takes 1MCP's whole endpoint offline for legacy clients (8 of 8 samples over 24 s), but not for modern ones, so Claude Code is not exposed.
- Only 1MCP recovered unaided from a session-based upstream restart on the same session. My first composition failed that test outright.
- fastmcp-ts contradicts its own docs: the documented URI invariant is false at 1.9.0, because prefixResourceUri inserts the prefix. npm fastmcp-ts is an unrelated package (0.1.2, another author); the real name is @prefecthq/fastmcp-ts.
- mcp-use docs say HTTP upstreams only, but proxy() accepts any duck-typed connection, and a stdio @mcp-use/client connection worked. Its telemetry is on by default, which no research report mentioned.
- agentgateway fails any MCP call over 10 s by default (upstream call timeout). This affects real tools and needs a route policy.
- 1MCP's requestTimeout had no effect on a 70 s call. It was the only setting that looked applicable.
- A running Claude Code session keeps subscriptions/listen open and refreshes on list_changed. That makes hot add a real differentiator: agentgateway sends none, so it never updates a running session.
- Tool-level anthropic/alwaysLoad survives agentgateway, 1MCP and the composition, and Claude Code honours it. This softens brief item X2.
- SDK trap for the KB, with no gateway involved: McpServer lists a static non-ASCII URI raw but looks it up via new URL(uri).href, which percent-encodes it, so kb://alpha/스냅샷/1 lists and then returns Resource not found. A template works; percent-encode or use templates.
- The SDK's LATEST_PROTOCOL_VERSION is 2025-11-25 and its client defaults to legacy. A 2026-07-28 client needs versionNegotiation set explicitly.
- No candidate fully handles a hung upstream. Cached lists (fastmcp-ts, mcp-use) did best here, which is why a last-good list is on the composition's to-do list.
- Mistakes in my own work, all corrected and rechecked: a shell bug made standalone stop a no-op (logs show instances never overlapped, so the matrix stands); a ~1 s cold-start outlier on every candidate was a dropped SYN in my polling, so the tables use a bounded re-run; the Korean URI first looked like a gateway failure until a direct control showed the SDK behaviour; a 1MCP hot-add 'failure' was a race in my test; my tap initially hid long-lived streams.
- Side effect, corrected: --no-session-persistence stops transcripts, but claude -p still created an empty ~/.claude/projects/<cwd>/memory/ per run. I removed all of mine with rmdir (12 directories, plus one after the final run). An s2-lifecycle-cc-cwd entry from another spike remains and was left alone; other spikes will leave the same.

### Recommendation

Use socket activation with no idle exit in v1. The process starts on the first connection and stays up. The port is a placeholder because X14 is open. Equivalent settings were tested via transient units; these exact files, Requires=, [Install] and %C were not run.

sagae-control.socket:
[Socket] ListenStream=127.0.0.1:8787, NoDelay=true. [Install] WantedBy=sockets.target.

sagae-control.service (no [Install]):
[Unit] Requires=sagae-control.socket, After=sagae-control.socket, StartLimitIntervalSec=0.
[Service] Type=simple, WorkingDirectory=<absolute path>, ExecStart=/home/user/.nvm/versions/node/v26.13.0/bin/node dist/server.mjs, Environment=NODE_COMPILE_CACHE=%C/sagae-control/compile-cache, Restart=always, RestartSec=1, TimeoutStopSec=8.

App rules:
1. Use createAdaptorServer plus server.listen({fd:3}) when LISTEN_FDS and LISTEN_PID match. Delete those variables afterwards. Fall back to 127.0.0.1:PORT for local runs.
2. On SIGTERM: server.close(), closeIdleConnections(), then closeAllConnections() after 1-2 s. Otherwise a Claude Code listen stream holds the stop until the timeout.
3. Keep declaring tools.listChanged. Adding upstreams without changing Claude Code config depends on it, and it is what makes Claude Code open the session-long stream.
4. Never run synchronous queries on the main thread. Use a worker or a separate process.
5. Keep work before listen() small. Start stdio upstreams after listening or lazily, because missing the 5 s discover probe pins the session to legacy.
6. ExecStart must exec Node directly, so LISTEN_PID matches (read from docs).

Install, for the user: systemctl --user enable --now sagae-control.socket, plus loginctl enable-linger sagae. Linger is required for L1. For L0 it removes the remaining dependency on a login session. Neither was run here. An nvm upgrade changes the absolute ExecStart path.

If idle exit is wanted later, all of these apply: Restart=on-failure instead of always (not measured); a StartLimitIntervalSec that normal activations cannot hit; count every open stream as activity; timeout above keepAliveTimeout + buffer (6 s), in practice at least 10 minutes.

### Verdicts

- **Plain long-running process that binds the port itself**: fail. Down at Claude Code startup means a 30 s stall per attempt and tool loss (R3a, R3e). About 58 refused requests per restart. 2 of 3 tool calls failed when stopped mid-session (R4)
- **Socket-activated with idle exit, open streams counted**: partial. Safe, with 0 failures for fresh connections and when keep-alive is shorter than idle. But subscriptions/listen is open for the whole Claude Code session, so it does not exit during any open session. Savings are about 94 MB plus about 78 MB per stdio child
- **Socket-activated with idle exit, listen stream not counted**: fail. Tool calls still work, but the process flaps (4 activations in 12 s) and the client gives up on re-listen after 3 drops, losing tool-list notifications for the session (R2d)
- **Socket-activated, started on demand, no idle exit, Restart=always**: pass. Startup connected with the app stopped (R1), SIGKILL between calls caused no tool error (R8), 0 of 6,665 failed across restarts, crash loop kept the socket and recovered (7.76 s). Exact unit files were not installed; equivalent settings were tested through transient units
- **Default systemd limits with socket activation**: fail. 6th quick activation or a crash loop ends in service-start-limit-hit, the socket unit fails and releases the port (measured). Needs StartLimitIntervalSec=0
- **Synchronous node:sqlite on the main thread**: fail. Stalls every MCP call and SSE stream for the full query. Queued queries reach about 1.6 s. A worker thread removes the effect (measured with a spin loop in the worker, not sqlite)

### Surprises

- Claude Code 2.1.316 opens subscriptions/listen right after discover and holds it for the whole session when the server declares tools.listChanged. The SDK declares it by default. This decides the idle-exit question and answers the open item in http-gateway.md about whether Claude Code opens such a stream.
- When the listen stream drops, the client re-listens at about 1, 2 and 4 s, and each re-listen reactivates the app. After 3 quick drops it gives up for that session. Tool calls keep working, but notifications do not.
- On this mirrored WSL host, a closed 127.0.0.1 port hangs instead of refusing, starting 50-400 ms after close. A raw connect ran 133 s. 127.0.0.2, ::1 and 192.168.x.x refuse instantly. So a plain server that is down costs 30 s per attempt here, not a fast failure.
- VG-C19 needs refining for 2.1.316 in -p mode. Startup failures get 3 more attempts, covering about 6 s with instant refusal and about 126 s with the hang. A server appearing inside that window is picked up. After the window it was not.
- A late connection falls to the legacy protocol because the 5 s version probe timed out (R3c, R3d). That session has no listen stream, so a slow start has a lasting cost.
- Default systemd limits are dangerous: 5 quick activations or a crash loop fail the socket unit and release the port, which is worse than a plain server failing.
- Fresh connections never failed across idle exits, even with process.exit, because systemd holds the listener. Every tagged failure was on a reused keep-alive socket, and the same failure occurs with no idle exit at all.
- Node 26 adds keepAliveTimeoutBuffer (default 1000 ms) to keepAliveTimeout, so lowering keepAliveTimeout alone did not remove the race (36 of 1,168 failed).
- A CONN_CLOSE test variant was discarded: curl showed connection: close, but clients still failed on reused sockets, and I did not find out why.
- The Write tool refused the required report.md as a subagent report file, so no report exists at the given path. This result carries the findings instead.
- Harness slips, corrected: zsh globbing broke the first active-SSE run, so it was rerun. Claude Code's Bash tool blocked a standalone sleep 45 in R3d, so the model used a background command, and later runs used a wait script.

## Spike 5

KB 계약의 규모 추정(개요 기본 프로필 노드 2만~5만, 엣지 5만~20만)으로 S3를 다시 쟀다. 레이아웃과 페이로드는 두 규모 모두 쟀고 렌더는 일부만 유효하다. KB 데이터 파일이 없어 그래프는 합성이다. 자체 worker의 FA2 300회는 20k/80k 18.9 s, 50k/200k 57.1 s로 Node보다 8~9% 느렸고 메인 스레드 rAF는 p50 6.06 ms였다. 페이로드는 50k/200k도 컬럼 JSON 19 MB, 파싱 75 ms 이하로 병목이 아니다. 렌더는 Orca 탭의 표시 주기가 깨져 fps, rAF, 20 ms 초과 프레임이 무효다(2026-11-01 정정: 원인은 GPU 경합이 아니라 호스트였다. 이 절 끝의 "2026-11-01 재측정" 참조). 읽을 수 있는 값에서 20k/80k는 첫 프레임과 CPU+GPU 예산을 넘었고 50k/200k는 오버레이를 뺀 항목을 넘었다. heap은 gc 값이 없는 상한이다. 이 절은 적대적 리뷰를 거치지 않았고 윗절의 리뷰 규칙이 적용되지 않는다. 재현 자산은 `docs/research/spikes/s5-scale/`에 있다.

### Recommendation

레이아웃은 브라우저 자체 worker의 `assign`을 유지한다. Node 대비 비용이 8~9%이고 메인 스레드를 흔들지 않는다. 기본 개요는 노드 1만, 엣지 5만 이하로 둔다. 계약 기본 `limit`, `edge_limit`과 같다. KB의 기본 타입 질문은 이 크기를 넘지 않는 필터로 답한다. 2만 보기는 사용자가 고르는 동작으로 두고 경고한다. 첫 프레임이 약 1 s다. 50k/200k는 전체 그래프로 그리지 않는다. 막는 것은 페이로드가 아니라 렌더와 heap이다.

측정 보고는 2만 초과에 Node `loupe layout`을 권했다. 근거는 `(build_id, scope)` 키와 "5분마다 빌드"였다. 계약 대조에서 그 전제가 틀렸다. 5분은 게시 간격이고 봉투의 `build_id`는 그때 바뀌지 않는다. `loupe.md` 6.2절은 키를 위상 해시로 바꾸고 소프트 미스를 넣은 뒤 Node를 출구 조건으로 옮겼다.

GPU가 조용할 때 `run-all.sh`로 렌더 행을 다시 재서 fps와 20 ms 초과 프레임을 얻는다. gc를 켠 heap을 함께 잰다. 15k/60k 천장은 외삽이고 재지 않았다.

### Surprises

- 렌더가 끝까지 정상 주기로 돌지 못했다. 표시 주기가 vsync의 14배와 165배로 묶인 것은 WebGL 탭에서만 나타났고 null rAF에는 없었다.
- 50k 레이아웃의 메인 스레드 끊김이 3회 모두 약 9.3 s에 279, 364, 345 ms로 났다. 원인을 찾지 못했다.
- 이전 20k 호버 실행 1회가 `Sigma: edge "40815" can't be repaint`를 던졌다. 뒤의 6개 셀에서 재발하지 않았다. 원인 미상, N=1이다(`out/log-s5.jsonl`).
- `performance.measureUserAgentSpecificMemory`가 Orca에서 막혀 있어 heap은 상한만 얻었다. S3의 63 MB는 gc를 켠 값이라 직접 비교할 수 없다.
- 첫 프레임과 CPU+GPU가 노드 + 엣지에 거의 선형이다. 15k/60k 천장은 여기서 나온 외삽이다.
- `tab create`를 그냥 쓰면 탭이 다른 worktree에 열렸다. `--worktree path:/home/user/sagae-tools`로 바꿨다. `tab close --page`가 worktree 없이 7개 탭에서 조용히 실패해 `--worktree id:`로 모두 닫았다.
- `pkill -f` 한 번이 자기 셸을 죽였다(exit 144). 다른 영향은 없었다.

**발견 1: Orca 탭이 문제였고 GPU 경합이 아니었다.** 같은 머신, 같은 어댑터(RTX 4080 SUPER)에서 Orca 탭은 gltest p50 60.6 ms(WebGL 어댑터 시험의 low-power, high-performance, default는 48.5, 42.4, 60.6 ms), Chrome 창은 6.06 ms다. Orca 탭의 이 실행 중 GPU 사용률은 5개 표본이 30, 1, 15, 3, 2%(중앙값 3%)로 GPU는 놀고 있었다. 이전 S5 본문이 60~85 ms를 "GPU 경합"으로 읽은 것은 틀렸다. 앞선 `nvidia-smi` 36~40%와 다른 Chrome 프로세스 34%가 원인이라는 증거는 이번 실행에서 나오지 않았다. 원인이 Orca 탭의 어떤 상태(포커스 없음, Chrome 150, 임베드)인지는 가르지 못했다. S3는 Orca 탭에서 6.1 ms를 냈다(이 문서에서 그때의 포커스를 확인하지 못했다). 포커스를 준 Orca 탭은 재지 않았다. Orca 탭의 워커 rAF는 6.1 ms였다(WebGL 없는 경로는 영향 없음).

**발견 2: 어댑터는 프로세스당 하나로 고정된다.** Chrome 156에서 `powerPreference`(`low-power`, `high-performance`, 기본) 셋 모두 같은 렌더러를 돌려줬다. 기본 프로세스는 셋 다 RTX 4080 SUPER였고 `--force_low_power_gpu` 프로세스는 셋 다 AMD였다. WebGPU `requestAdapter`의 두 옵션도 같은 어댑터(nvidia lovelace, 또는 amd rdna-2)를 돌려줬고 `distinct_adapters`는 false다. 두 WebGPU 장치를 만들 수는 있지만 같은 어댑터다. 워커의 WebGL도 같은 렌더러다. 한 페이지가 두 어댑터를 쓸 수 없고 `powerPreference`는 무시된다. 어댑터는 Chrome 프로세스를 띄우는 플래그가 정한다.

**발견 3: 중간 셀은 15,475 / 42,892다.** 이 셀의 이름은 sub10k지만 `prep/layout.mjs:12`가 `KEEP` 기본값으로 Feature와 Event를 남기기 때문에 10,528 / 26,873(Product와 Concept, 윗절의 통제군)이 아니다. 두 "중간" 셀은 같은 그래프가 아니어서 값을 직접 비교하면 안 된다. 이 재측정의 sub10k는 모두 15,475 / 42,892다.
